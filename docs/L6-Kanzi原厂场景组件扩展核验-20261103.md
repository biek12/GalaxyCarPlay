# L6 Kanzi原厂场景组件扩展核验

2026-11-03，Asia/Shanghai。回应“原厂中央区域换地图、右侧换自定义Kanzi歌词组件”。这是技术核验与候选结构，尚未替换已确认产品架构或部署原厂HMI修改。

## 判断

Kanzi 3.6.9框架支持自定义节点、属性、消息与数据入口，以及组合多个KZB的Prefab/资源。本车`cluster-hmi`也包含真实的插件加载、资源加载、子节点管理和纹理更新实现。因此“在原厂Kanzi场景内新增地图/歌词组件”有源码及二进制依据，可以继续实施接入研究。

但本车尚未跑通新插件加载、原节点挂接和数据绑定，不能称为已有即插即用的原厂定制接口。当前只有原厂ELF、KZB及文本索引，没有可重建的原厂C++/Studio工程；需核验兼容的Engine/资源工具链及本车加载接缝。

上述addChild/setData/addKzbFile选定重载在`.symtab`中存在，但本轮对其精确符号名的`.dynsym`检索未命中。不能把文件里可反汇编的函数地址当作新插件可直接链接的导出API；也不等于本车没有其他可用重载。新模块需核验实际API集合、QNX AArch64/C++ ABI、类型注册和生命周期，不能随意链接另一套Engine后视为兼容。

另发现`RBStreamModule`（`0x7a4d00`）、`RBStream::getRenderTexture`（`0x7a6d68`）、`parseFile`（`0x7a78c0`）。其代码有图片向量、文件解析及动画回调；名称中的Stream不能据此解释成Android实时地图接收接口，本轮未将其当作原厂视频入口。

`ClusterHMI/application.cfg`只见显示、窗口、帧率等参数，尚未证明当前配置已启用外部插件。框架含loadPlugins代码不等于拷贝一个SO到目录就会自动执行。

## 两类组件的实现差别

**中央地图组件（候选名MapPane，并非已有类）**：在原厂场景中央容器挂接地图纹理节点；CarPlay111继续在Android产生完整地图，跨域传输把帧送给QNX中的组件桥，桥在Kanzi正确线程更新纹理，再由原厂Screen统一提交。显示位置在原厂场景中管理，不再要求独立全屏Screen窗口。

组件仍需要帧输入，KZB不能自行获取CarPlay画面。可以研究把自有接收消费逻辑移入组件桥，从而取消独立接收进程；这只是候选结构，原厂传输能否复用仍按前轮缺口核验。不能将“不另建窗口”写成“不再需要传输”，也不预先承诺GPU直导、零拷贝或性能收益。

中央原组件承担ADAS可视信息；准确节点和区域绑定还需追踪。设计应通过显示模式切换地图/原ADAS内容，并保留原告警与状态机的实际优先级；不能简单删除整份adas.kzb后称为局部替换。

**右侧歌词组件（候选名LyricsPane，并非已有类）**：多行Text Block、布局、裁剪、字体、当前行高亮和动画可以优先由标准Kanzi节点/Prefab组成，不必为每行歌词创建新native节点类型。桥提供曲目标识、时间、歌词文本、当前行及状态，再绑定组件属性。

当前本车`rightmenu.kzb.txt:16-24`与`ClusterDataSource.xml:513-521`可确认的是歌手、标题、封面等字段，尚未找到专门歌词属性。Android媒体Proto存在`lyricSentence/lyricContent`（`DIMInteraction/.../InteractionProto.java:699-709`），不等于这些字段已通过原厂QNX处理写入Kanzi模型。应逐段接通输入、QNX缓存、数据源属性与节点绑定。

用户既有歌词来源规则继续适用：原厂仪表链使用iPhone原始NowPlaying动态歌词；网络歌词只用于已有自定义仪表投屏需求。若未来把新Kanzi组件定义成新的自定义主题消费者，其歌词来源是产品选择，不能因改了绘制技术擅自切换。

## 组件包与加载边界

推荐核验“原厂Screen/数据源/状态机 + 独立组件KZB + 小型native桥”的结构。组件KZB不导出新的Screen；由集成逻辑加载、实例化并挂到准确容器。仅添加资源包不会自动替换现有Prefab实例，也不能假定同名Prefab覆盖正在使用的对象。节点查找、替换及恢复需在原厂UI生命周期内完成，避免用循环写属性压过原状态机。

这是复用原厂Engine与原厂场景的自定义实现；新增组件和桥仍是自有代码。下一决定性验证是兼容模块能否被本车HMI加载，并在指定非关键容器挂接一个可恢复节点。通过后再接歌词数据和地图帧，不能以宿主预览或加载函数返回替代目标可视验收。
