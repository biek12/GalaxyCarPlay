### 2.2 权限与应用身份

清单只申请自己用得上的权限：

- `FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_DATA_SYNC`：录制与写盘由本 App 前台服务承担（片段持续写盘属 dataSync）。
- `RECEIVE_BOOT_COMPLETED`：规格 S-REC-01「开机自动录制」的实现前提。
- `com.ecarx.autoservice.permission.CLIENT` + `<queries><package com.ecarx.autoservice/></queries>`：绑定 AutoService 的前提；缺任一项都连不上（摄像头设计稿 §3.1 已把这一条列为阶段 B 第一道门，本轮已补）。
- **不申请 `CAMERA`**：摄像头由 AutoService 采集，AutoRecord 不做 Camera2 调用，避免两个前台服务抢同一个相机节点。

### 2.3 不依赖 CarPlay 的设计

`:record` 只依赖公共契约客户端 `:auto-client`。FlymeAuto 视觉是"按本项目色阶与控件几何自绘"，不是引用 CarPlay 的 `:common` 资源——`L7*` 组件绑定 CarPlay 宿主 `R`（`config_l7_product_ui` 只在 CarPlay 为真），独立应用无法直接复用，`ServiceUi`/`ClusterUi` 是同样的先例。

## 5. 摄像头与契约路线（设计已定，代码未写）

按[摄像头接入链与契约设计](Camera接入链与契约设计-20261103.md)的结论执行：

- 摄像头域在 AutoService 内是**全新子系统**，当前工作树无任何 Camera2/`openCamera`/`cameraId` 代码，`eglPresentationTimeANDROID` 零调用。
- 契约走**路线 A**：新增独立 `IAutoCamera` 与独立绑定入口，`AutoContract.VERSION` 保持 4。理由是不构成既有语义变更，而升 5 会因客户端严格相等立刻打断已装 CarPlay/AutoCluster。
- 现有 `onSurface`/`role` 是"服务端生产、客户端消费"，方向与录制相反，不能复用。
- 客户端必须遵守：会话代次（generation）不符一律拒、`DeathReceiver` 兜底、release 幂等、"用户一键关闭摄像头"优先级最高。

**不写契约代码**的原因：先需要实车核验 12 项（相机可见性、权限/身份、原厂环视占用、相机时间戳时钟域等）。在核验前写 AIDL 会把未验证的假设固化成协议。

## 6. 设置与持久化口径

- 所有设置即时落盘（`SharedPreferences("record")`），界面改动不等待"保存"。
- 影响编码/写盘的字段（编码格式、硬软实现、分辨率、帧率、码率、关键帧、存储卷、配额、分段时长）**下一片段生效，当前片段不中断**；界面逐行显示该提示。
- 探测不通过的组合置灰并写明原因；找不到编码器/卷不可写时**拒绝并报错，保持原值**，禁止回退到另一种实现或另一个介质。
- 非法值回落默认并记日志（`非法值回落默认而不是当正常` 有单测）。

## 7. 存储口径

- 只持久化卷 **UUID**，不存绝对路径；解析不到即"卷已移除"，停止写入并报卷名。
- 目标目录必须真写探测（1 字节 + fsync + 删除），`canWrite()` 不作结论。
- 最低剩余 2 GB 默认；配额自动档＝32 GB 与介质一半取小；循环覆盖只删"最旧的、未锁定、已收尾、未在导出"的片段，永不格式化介质、不删非本 App 文件。

## 8. 编码口径

- 硬/软/未知三态只由 `isHardwareAccelerated()`/`isSoftwareOnly()` 判定，两位皆假算未知；不按 `OMX.qcom.`/`c2.android.` 前缀猜。
- 界面显示"将使用的实际编码器名"（`pick` 结果），并在片段清单里记录 create 之后回读的真名。
- H.265 在探测不到本机 HEVC 编码器前保持置灰；软件编码写明代价与"3 路及以上/四路软编禁止"。
- 码率＝`bpp 0.08 × W × H × fps`，四路合计与介质吞吐对比后再固化高档值（当前高档未实测）。

## 9. 段目录、状态机与原子落盘

```
AutoRecord/
  segments/20261103/20261103-221500-000/
    front.mp4 rear.mp4 left.mp4 right.mp4
    segment.json vehicles.jsonl events.json thumb.jpg
  index/index.db          # 可重建
  tmp/
```

收尾顺序固定：编码器 EOS → drain → `muxer.stop()` → `release()` → `fsync` → 原子改名 → 写索引。崩溃残留 `.writing`/`.partial` 必须被识别为未完成，不得出现在录像库的正常条目里。

## 15. 摄像头直连接入（2026-11-03 第四轮，覆盖原"只经 AutoService"表述）

### 15.1 决策

用户明确：**若 CAMERA 权限不需要 Service 代办授权，就不要绕 AutoService 转发画面**；AutoService 的价值收敛为
① 需要时自动获得 CAMERA 授权 ② 自动扫描出所有能通的 cameraId 供选择。据此改为**本应用直连 Camera2**。

理由（不只是"少一层"）：
- 实测相机缓冲恒 6 MB、真实 JPEG 0.55–0.83 MB，逐帧跨进程转发等于把 4×6 MB 的搬运成本常态化；
- 实测四路并发开流可行（0.5 s 内首帧），不存在"必须由服务串行调度"的约束；
- 录制要在本进程编码写盘，帧如果先出进程再回来，反而多一次拷贝。

### 15.2 落地内容

| 项 | 实现 |
| --- | --- |
| 权限 | manifest 声明 `permission.CAMERA` + `uses-feature required=false`；运行时 `checkSelfPermission`，未授予则申请一次；**固件预授予时无需弹窗**（同一条路径覆盖两种形态） |
| 方向标定 | `CameraLayout` + `CameraLayoutStore`（独立 `record.camera`，不随"恢复默认设置"丢失）；默认假设 A（0=左 1=右 2=前 3=后），诊断页可逐路改 cameraId，改数据不改代码 |
| 采集 | `DirectCameraSource`：每路一个 `ImageReader(JPEG 1280×800, maxImages=2)`，**自驱动单次 capture**（一帧处理完再请求下一帧，HAL 不排队） |
| 帧率 | 四宫格 8 fps/路、单路放大 15 fps；达不到就如实变慢，不硬追（实测单张 268–478 ms） |
| 解码 | 四宫格 `inSampleSize=4`（320×200），单路放大才全尺寸；这是"最少资源"的关键一处 |
| 截断 | `CameraProfile.jpegEndOffset` 按 JPEG 段结构走（跳过 EXIF 内嵌缩略图里的假 EOI），只取有效字节 |
| 生命周期 | 页面 `onShown` 开流、`onHidden`/`onPause` 停流；单路放大时**释放其余三路**，不空占相机 |
| 错误 | HAL 异常文案原样保留（如 `Illegal argument to HAL module for camera "N"`），按缺路证据展示，不静默跳过 |
| 预检 | 新增 `camera-layout` 检查项：方位映射不合法直接拦在预检，避免四路装错方向 |

### 15.3 容量口径随之修正（重要）

实测相机 JPEG 只有 **1280×800**，此前按 1080p 估算的回溯时长是错的：

| 项 | 修正前（假设 1080p） | 修正后（实测 1280×800） |
| --- | --- | --- |
| 单路码率 | 4.15 Mbps | 2.05 Mbps |
| 四路合计 | 16.6 Mbps | 8.19 Mbps |
| 32 GB 可回溯 | ≈4.6 小时 | **≈9.3 小时** |

同时收敛两个不可用选项：**1080p 置灰**（原生只有 800 高，禁止上采样）、**30 fps 置灰**（实测上限 25）；画质预设从三档改为两档（省空间 720p15 / 均衡 原生25fps）。
