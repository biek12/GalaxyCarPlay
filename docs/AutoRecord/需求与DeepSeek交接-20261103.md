# AutoRecord 四向记录仪需求与实施交接

日期：2026-11-03。版本：**v0.2**（v0.1 需求整理稿 + v1.1 规格评审回写的 R13 取证主链路与范围声明）。交付对象：用户及后续 DeepSeek 开发会话。

**本轮只整理需求、核对参考源码和当前工程接点；没有实现 AutoRecord，没有编译、安装或连接车辆。** 本文将“用户明确要求”“截图中可见能力”“实施建议”“待核验技术事实”分别标注，建议参数不自动升级为用户决策。

## 1. 产品定位与已确认范围

- 在 GalaxyPlay 工程增加独立 **AutoRecord 四向行车记录仪**，与 CarPlay、AutoService、AutoCluster 并列。
- 前、后、左、右四路原车摄像头录像，连同车辆运行状态记录、同步回放和事件检索，构成完整目标；不能只实现四宫格预览。
- **实时摄像头画面和车辆数据统一来自 AutoService。** AutoRecord 不自行连接厂商车辆 SDK、Camera2、ADB、Root 或认证材料。历史录像、索引、用户配置由 AutoRecord 自己管理。
- 参考 EVCam 的 L6/L7 摄像头接入经验，按本项目边界重新组织；三张截图是目标能力参考，不是 EVCam 已实现全部能力的证明。
- 首验目标沿用：银河 L6，2023 Max，FlymeAuto 2.3.1，Android 11；L6 优先，其后核验 L7。当前产品 UI 适配同一 8155 竖屏形态，不照搬截图中横屏布局。
- 本轮授权止于需求和交接；后续开发、现场连接、安装与摄像头共存验证按用户后续指令执行。

## 3. 功能需求

以下 R01–R08 为对用户目标及截图能力的整理；R09–R12 为使记录仪可持续使用而提出的配套建议，尚需用户确定产品取舍。

**页面与设置的落地细节已单独定稿**，本文为能力与证据层，实施以[页面功能与设置规格](页面功能与设置规格-20261103.md)（v1.0，逐页 P1–P14、设置项 S-*、状态矩阵）为准；样式 token 见[FlymeAuto 样式基线](FlymeAuto样式基线-20261103.md)，编码/存储口径见[技术口径](编码与存储技术口径-20261103.md)。用户已确认 AutoRecord 的 UI 风格**继续继承 CarPlay 的 FlymeAuto 风格**。

### R01 四路实时画面

1. 默认四宫格：左上前、右上后、左下左、右下右，每格有清晰方向标识；可切换任意单路大画面，再切回四路。
2. 实时画面显示当前录像状态、已录时长、车辆数据状态和存储状态；错误须指向具体摄像头或数据源。
3. 切换画面、进出页面、日夜切换不改变四路录制范围，不反复关闭再打开摄像头。
4. 保留完整原始视野，不为填满卡片默认裁掉有效画面。旋转、镜像和方向标定由 AutoService 的目标车型配置提供。

### R02 手动、自动与后台录制

1. 支持手动开始/停止；录制状态以真实编码输出与文件写入结果为准，按钮点击或摄像头打开不算录制成功。
2. 提供自动录制、启动恢复设置，记录开启意图；界面退出和息屏不应自行终止已开启的录制。
3. 自动录制的触发条件、开关默认值列入第 10 节待定项；不得自行把“息屏”解释为“锁车”、把 App 启动解释为车辆上电。
4. 用户主动关闭录制后，旧回调、恢复任务及其他页面不得重新开启；AutoService 全局关闭选择同样有效。
5. 四路独立报告首帧、实际写入、断流和恢复。某路异常必须标识录像缺路及时间范围；不能复制其他方向画面假装四路齐全。完整四路仍是验收目标。

### R03 分段与录像会话

1. 连续录像按片段保存；一个片段应将四路视频、车辆历史数据、事件和缩略图作为一个逻辑记录管理。
2. 建议默认 60 秒，与截图约一分钟片段一致；1/3/5 分钟可配置属于建议，截图未证明其设置菜单。
3. 分段后可连续回放；记录实际帧时间、分段边界及缺口。不能仅凭文件名相同宣称四路同步或无缝。
4. 断电、进程异常或存储中断后，已完成片段仍可读；未完成片段检查后标为可恢复、部分有效或损坏，不能进入普通完整录像列表冒充正常。

### R04 录像库

1. 日期分组、片段总数、倒序排列；两列卡片适配竖屏，支持大列表分页或按需加载。
2. 卡片显示四向缩略图、开始时间、实际时长、存储位置、是否含车辆数据、已播放/未播放，以及异常或缺路标识。
3. 支持日期、时段、录像类别和状态组合筛选；类别/状态选项须随产品确定，不把截图未显示的选项写为既有需求。
4. 进入录像回放、实时画面、开始/停止录制和设置均有明确入口；状态文案反映后台真实任务。

### R05 四路与车辆数据同步回放

1. 支持四宫格及前后左右单路切换，播放/暂停、拖动进度、前后跳转、当前/总时长；倍速为建议功能，档位待定。
2. 四路共用一条会话时间轴。拖动或跳事件后，四路画面、数值条、图标条和事件游标一起定位。
3. 回放只读录像当时保存的数据，离线可用；不能叠加当前实时车速、当前转向灯或今天的车辆状态。
4. 拖动后根据目标时刻之前最近的有效历史样本恢复状态，再按历史时效判定。缺数据显示未知/缺失，不补零、不跨断流区间无限沿用。
5. 不能通过拉伸某一路时间或按固定帧数重写时间来制造同步；晚到首帧、掉帧、无帧区间均应保留。

### R06 车辆数值与图标记录

截图的数值和状态均应“录下来并可回放”，不能只做实时装饰。下表的源码存在不代表每项已在指定固件实测，更不等于枚举含义已经核验。

| 内容 | 当前 AutoService 候选键/实现 | 状态与实施要求 |
| --- | --- | --- |
| 日期、时间 | 新摄像头会话的统一时钟描述，待扩展 | 由服务提供录像时钟基准；记录时区和时钟校正，不用视频文件修改时间代替 |
| 车速 | `displaySpeed` | 目录已存在，km/h；不得混用实际车速或巡航设定值 |
| 挡位 | `gear` | 目录已存在，P/R/N/D 映射 |
| 发动机转速 | `rpm` | 目录已存在，rpm 与除数 2；需保留来源与有效性 |
| 转向角 | `steeringAngle` | 目录已存在；正负方向和目标固件量纲待核验 |
| 油门、制动踏板 | `accelerator`、`brake` | 目录已有百分比声明；不得把制动踏板量与制动灯状态混为一项 |
| 制动信号 | `brakeLight` | 目录存在原始状态；作为事件前须核对原厂枚举 |

| 巡航状态、设定速度 | `cruiseState`、`cruiseSetSpeed` | 已有 off/standby/active 和 km/h 声明；与横向辅助分开 |
| 近光、远光 | `lowBeam`、`highBeam` | 目录已存在原始状态，需核验激活枚举 |
| 自动远光 | 待从目标固件目录及本地材料定位 | 需求保留；不能用远光开启状态推断自动远光功能启用 |
| 示宽灯 | `positionLights` → `property.10041` | 已有兼容别名，核验原始枚举 |
| 后雾灯 | `property.10042` | 已有原始目录项，待服务端补语义别名/枚举 |
| Auto Hold | 待定位 | 不用驻车制动状态替代 |

| 油量、电量 | `fuel`、`soc` | 目录已存在，百分比 |
| 总续航 | `fuelRange`、`evRange` 为分项候选 | 当前未见已核验的总续航公共键；由 AutoService 核对原厂显示口径后发布，不能擅自相加当原厂总续航 |

### R07 多轨驾驶事件时间轴

截图可识别的基础轨道：**刹车信号、油门、横向辅助启用、横向辅助退出、巡航启用、巡航退出**。

1. 与录像共用时间坐标，当前播放位置显示竖向游标；区间状态用条带，离散启用/退出用点或菱形标记。
2. 支持按事件类型筛选、选中事件/全部事件、事件数量、上一/下一事件及点击跳转到对应画面；轨道有名称、颜色与清晰选中态。
3. 油门条保留对应踏板值及区间，不只有“踩/没踩”一个布尔值。阈值、去抖、合并间隔须版本化保存，默认数值不在本稿中拍定。
4. 巡航待机与激活分开，横向辅助与纵向巡航分开；退出原因仅在源确实提供时显示。
5. 状态首次到达只建立已知基线。来源掉线、过期或会话变更标为未知区间，不能合成一次“退出”，也不能重连后伪造“启用”。
6. 事件必须能追溯到原始样本、来源时刻和映射版本。已轮询观察到的变化与源事件回调分别标记；不宣称轮询可恢复两个采样点之间没有观测到的短事件。

### R08 界面与设置

- 沿用项目 FlymeAuto 日夜风格、字体与触控尺度，竖屏页面分为录像库、实时画面、同步回放、设置；截图用于功能对标，不要求逐像素复刻。
- 回放中四路画面、信息条、播放控件和事件时间轴合理分配空间；事件轨道可展开，单路可放大。
- 录制策略、分段、存储、容量、数据展示、自动运行等设置有明确当前值。涉及自动运行与资源占用的开关实际控制生命周期并持久化。
- 不把摄像头 ID、ADB 命令和车型内部属性号放进正常用户流程；诊断另设入口。

### R13 取证主链路（v0.2 新增，功能补强）

R01–R08 描述的是"能力"，缺的是把能力串成用户真正要做的那件事。记录仪的第一价值不是"能录四路"，而是**出事时能立刻拿出一段可交付的证据**。因此新增一条端到端需求，作为一等功能：

1. **一键锁定最近片段**：任意页面（含实时画面）提供该动作，一次操作锁定"当前正在写的片段 + 最近一条已完成片段"。只锁一段在事件跨分段边界时会丢证据，故必须成对锁定，并给出"已锁定 2 段"的实际回执。
2. **事件标记参与保留保护**：按已有制动/油门/横向辅助等信号阈值给片段打"事件标记"，含事件的片段不参与循环覆盖。**文案红线**：只称"事件标记"，不得宣称碰撞检测或事故认定。
3. **保留窗口必须可见**：界面用"可回溯 ≈ X 小时"表达配额，而不是只给 GB。按 1080p25 四路约 16.6 Mbps 估算，1 分钟段约 124 MB，32 GB 配额约 4.3 小时——这意味着**隔夜取证基本必然丢失**，产品必须让用户看见这个事实并给出锁定/导出路径，不能靠用户自己换算。
4. **导出并入片段操作**：取证时"锁定 → 看事件 → 导出"应连贯完成，导出作为片段操作面板里的就地动作，不另设需要重新找片段的独立页面；支持跨分段区间合并为一个文件，并保留原始颗粒度。
5. **范围声明**：本期**不做停车监控（熄火后继续录）**。理由：依赖车辆上电与 AutoService 会话，熄火后采集不可保证，且涉及电瓶与区域法规，不做未核验承诺；后续单独立项。

验收口径：从"决定留证"到"证据已受保护"≤2 次操作；到"可交付 MP4"≤5 次操作；锁定的片段在循环覆盖中不被删除；事件标记不出现事故认定类措辞。

## 4. AutoService 与 AutoRecord 的责任建议

**数据来源归属已确认，编码和存储的以下拆分是实施建议，尚未落地。**

```text
L6 原车四向摄像头 ─→ AutoService 摄像头适配/会话/时间戳/图形分发
                          ├─→ AutoRecord 预览 Surface
                          └─→ AutoRecord 编码输入 Surface → 四路视频/片段存储
L6 车辆只读来源 ───→ AutoService v4 按需订阅/标准化/时效
                          └─→ AutoRecord 历史样本/事件派生/索引
                                                    ↓
                              同一会话时间轴 → 同步回放/事件检索/本地导出
```

| 归属 | 责任 |
| --- | --- |
| AutoService | 唯一真实摄像头采集 owner；目标车型能力与方向配置、权限/Root协调、原厂环视占用协作、图形输出、帧元数据；唯一车辆采集与标准化入口；现有用户关闭选择 |
| AutoRecord | 录制业务及后台任务、编码器和写盘、片段/数据索引、历史样本、事件规则与时间轴、回放、导出及自己的界面；不取得 SDK 或 Root 身份 |
| contracts/client | 摄像头会话与输出契约、车辆订阅消费、身份/版本、死亡/重连、时间描述与错误语义；不打包实际车型采集实现 |

建议新增模块 `:record` → `galaxy/record`，应用显示名 AutoRecord。applicationId 尚未确认，候选 `com.galaxy.autorecord`，不能把 AutoService 已确认的 `com.ecarx.autoservice` 命名推广为 AutoRecord 的既定身份。根工程名及 CarPlay 身份不变。

摄像头端必须在 AutoService 内部拆分设备会话、图形输出与元数据职责，不继续向 `AutoService.kt` 堆完整录像业务。AutoRecord 不依赖 CarPlay 的 `:common`/`:shared` 协议核心。

## 6. 新增摄像头契约必须表达的内容

本节为协议设计要求，**不是现有 API**；不在需求稿中锁死尚未实现的方法名或擅自将公共版本改成 v5。

1. **能力查询**：当前车型/固件、方向与实际 cameraId、原生尺寸/FPS范围、像素格式、旋转/镜像、并发限制、访问身份及状态。引用 EVCam 的枚举位置映射仅作参考。
2. **会话租约**：owner、sessionId、generation、用途（预览/录制）、明确申请/释放；客户端死亡和服务重启使旧代失效。摄像头功能需要可持久化的一键关闭，恢复任务遵守用户选择。
3. **图形输出**：AutoRecord 创建预览或编码器输入 Surface，按方向交给 AutoService 输出；服务持有自己的借用引用并在停止/死亡时释放，AutoRecord 释放自己的 Surface/编码器。每个生产端所有权清楚，不把同一 Surface 同时交多个生产者。
4. **大数据与元数据分开**：帧像素走 Surface/图形缓冲区，禁止每帧 Binder Bitmap/byte[]；小批帧元数据描述方向、frame序号、摄像头时间戳、时钟类型与转换关系。元数据与实际输出帧须可匹配，队列有界。
5. **状态**：区分授权不足、等待原厂释放、首帧、活动、断开、恢复、主动停止；报告实际帧率、缺帧和原因。原厂抢占协作按目标固件真实行为实现，不强关原车环视、杀原厂进程或改全车摄像头策略。
6. **时间对齐**：核对 Camera 时间戳来源，建立到统一单调时间轴的映射；四路起点不同和时钟校正显式记录。保存 UTC/本地展示基准及单调时钟锚点，重启另建 clock epoch，避免墙钟回拨影响顺序。
7. **兼容与权限**：按新增接口实际兼容性确定版本协商。当前 AutoClient 严格相等，若升级公共 VERSION，CarPlay/AutoService/AutoCluster/AutoRecord 的契约和 APK 配套核对；禁止只改服务端破坏已安装消费者。

## 7. 录像数据与事件保存建议

- 一次 recording session 下包含多个 segment；每段有四路文件清单、实际覆盖时间、分辨率/编码、缩略图引用、数据/事件文件或数据库引用、完整性状态及 schemaVersion。
- 每路保留其时间戳到统一会话时间的对应，不能把四路各自首帧全部重置为“同一个0”而丢掉首帧时间差。
- 每个车辆历史样本保留 key/value/unit/source/status/receivedAt/sourceTimestamp（若有）/epoch/maxAgeMillis，以及接收和归档位置；不可只保存最终合并快照。
- 每个事件保留 eventId/type/start/end或point、source epoch/sequence、触发样本引用、规则版本及时间精度。规则变化后不静默改写历史语义。
- 片段完成前保持 writing 状态，收尾成功后再发布可播放索引。清理与导出按片段引用计数或事务协调，禁止删掉仍在写入的文件。
- 采用四路独立视频加旁路数据作为建议原始格式，回放组合四宫格；是否另存拼接视频由用户决定。数据库、旁路文件具体格式由实现选定并说明恢复、升级和导出方式。
- 原始车辆样本为用户明确需要的本地录像数据，**不得写入诊断日志或随测试包上传**。公开资料不含认证材料、车机/手机标识、密钥；本地导出由用户选择。
