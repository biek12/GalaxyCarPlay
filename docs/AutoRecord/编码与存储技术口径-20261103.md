# AutoRecord 编码与存储技术口径

日期：2026-11-03。版本：v1.0。服务对象：[逐页规格](页面功能与设置规格-20261103.md) 的 §6、P6/P7/P11，以及 S-STOR-01…05、S-ENC-01…06。

**本轮只读研究与文档：未连接车辆、未安装、未编译、未跑 Lint、未改源码、未提交。** 本文所有"本车"结论一律**待核验**；实测结果出来后必须回填并按实测修正选项表。8155 有多少编码器、几路并发、HEVC 能否编码，本轮**不断言**。

分级：【平台】Android 官方 API/文档明示；【源码】本仓库工作树实际存在（附 `file:line`）；【待核验】必须实车实测；【工程约定】本项目选择的实现约定或经验参数，非平台强制、非实测。

## 0. 一页结论

1. 硬/软只能用 `MediaCodecInfo.isHardwareAccelerated()`/`isSoftwareOnly()`（API 29+）判定，禁止按 `OMX.qcom.`/`c2.android.` 前缀猜。【平台】
2. "软编码"不是一个开关，而是**自建取帧链**：Surface 只能喂硬编码器（零拷贝）；跑软编必须自己把像素取到 CPU 并转成编码器接受的 YUV。
3. **四路并发软编不可假设**：软编吃 CPU，与 CarPlay 投屏、Cluster 渲染、HAB 合成抢同一批核；书面实例数上限不证明满帧。
4. **PTS 真实性取决于生产端**：Surface 输入的 PTS 来自入队 buffer 时间戳，AutoService 必须对每帧调 `eglPresentationTimeANDROID`。本仓库**零调用**（已 grep）——新增项，不是既有能力。
5. **U 盘可写性边界**：App 专属目录（`getExternalFilesDirs` 下标≥1）零权限可写但随卷消失；写根目录/让用户可见才需要 SAF。仓库**无**卷枚举、`StatFs`、`MediaMuxer`、视频编码器——全为新代码。可复用的既有资产是 codec 探测页的**方法论**（真跑一次、失败停在具体阶段、回读实际实例名与硬软位）与存储统计的线程纪律，**不是编码器本身**。

## 1. 硬/软编码：含义与判定

| 说法 | 实际含义 |
| --- | --- |
| 平台"硬编码器" | 厂商/SoC 组件，通常接受 Surface 零拷贝输入并完成转换压缩 |
| 平台"软编码器" | `c2.android.*`/`OMX.google.*`，输入 ByteBuffer YUV，压缩由 CPU 完成 |
| 设置项 S-ENC-02 "软件编码" | 选软件编码器编码；连带要求自建 YUV 取帧链（§2） |
| 上游 EVCam 的"软编码" | 其 `CodecVideoRecorder` 输入为 Surface（[需求稿 §8](需求与DeepSeek交接-20261103.md)），**不能证明纯 CPU 软编**，不可当作能力证据 |

```kotlin
// 唯一正确写法：只查清单，不创建实例
MediaCodecList(MediaCodecList.REGULAR_CODECS).codecInfos
  .filter { it.isEncoder && it.supportedTypes.any { t -> t.equals(mime, true) } }
  .map { Caps(it.name, it.isHardwareAccelerated, it.isSoftwareOnly, it.isAlias) }
```

- 仅 `hardware && !software` 是硬编；`software` 是软编；**两位皆假＝未知实现**，必须显示"未知"而不是猜。三态先例：[`GalaxyCodecProbePage.kt:113-117`](../../galaxy/common/src/main/java/com/shilapi/xcertplay/GalaxyCodecProbePage.kt#L113-L117)。
- 别名 `isAlias` 算两条名字但**不是两个并发实例**；只按名字去重会把一路算成两路。[`AndroidMediaSink.kt:1532`](../../shared/src/main/java/com/shilapi/xcertplay/media/AndroidMediaSink.kt#L1532) 已在读该字段。
- 前缀判断只有一处合法：识别 QTI 组件以附加厂商参数，属显式实验条件，不是判定依据——[`GalaxyCodecProbeRecipe.kt:50`](../../galaxy/common/src/main/java/com/shilapi/xcertplay/GalaxyCodecProbeRecipe.kt#L50) `isQti()`，仅被 `:53` 的 QTI 前置校验使用，配套注释"参数接受不证明生效"。下列先例提供**方法论**，不是可直接引用的编码实现：

## 2. 输入形态：Surface vs ByteBuffer YUV

| 维度 | Surface（硬编首选） | ByteBuffer YUV（软编必需） |
| --- | --- | --- |
| 数据路径 | 生产端 EGL→图形缓冲→编码器，**不经 CPU** | Surface→CPU 取帧→色彩转换→`queueInputBuffer` |
| 谁产 YUV | 无需 | AutoRecord 自己（ImageReader 或 glReadPixels） |
| 色彩格式 | `COLOR_FormatSurface` 隐式协商 | 必须显式设 `KEY_COLOR_FORMAT` 且属 `colorFormats` 列出值（如 `COLOR_FormatYUV420Flexible`）【平台】 |
| 行跨距 | 不涉及 | 必须处理 `rowStride`/`pixelStride`，不能假设 = width |
| PTS 来源 | **入队 buffer 时间戳**（生产端写入） | 自己填 `queueInputBuffer` 的 `presentationTimeUs` |
| 并发成本 | 主要是硬件实例数 | 实例数 + CPU 拷贝/转换 × 路数 |
| 本仓库实现 | 无（新建） | 无（新建）；"Surface→CPU 逐行拷贝"写法已在 AutoService 存在 |

**PTS 由谁决定（关键接缝）**：Surface 编码器把每个入队图形缓冲的时间戳当 PTS。生产端用 EGL 画到编码 Surface 时，必须在 `eglSwapBuffers` 前调 `EGLExt.eglPresentationTimeANDROID(display, eglSurface, frameTimeNanos)`（API 18+，<https://developer.android.com/reference/android/opengl/EGLExt#eglPresentationTimeANDROID(android.opengl.EGLDisplay,%20android.opengl.EGLSurface,%20long)>），否则时间戳退化成 swap 时刻，四路抖动、掉帧、首帧差被抹平。【源码】本仓库**零调用**；现有 EGL 封装只有 `window/current/swap/destroy`（[`GalaxyEglContext.kt:31-41`](../../galaxy/service/src/main/java/com/ecarx/autoservice/projection/GalaxyEglContext.kt#L31-L41)）。→ 这是新增摄像头契约的**强制字段**（对应[需求稿 §6.4/6.6](需求与DeepSeek交接-20261103.md)）：AutoService 必须逐帧设置呈现时间且取自相机帧时间到统一单调时钟的映射；AutoRecord 不得用"收到帧的时刻"顶替。

软编自建取帧链两条路线：

| 路线 | 做法 | 代价/风险 |
| --- | --- | --- |
| A `ImageReader`(YUV_420_888) | AutoService 输出到 AutoRecord 的 `ImageReader.surface`，`acquireLatestImage()` 取 3 plane 按 `rowStride` 逐行拷入编码器输入 | 最省 CPU（无 RGBA 中间态）；仍需处理 3 plane/stride/丢帧语义 |
| B EGL+`glReadPixels` | 渲染到 pbuffer/FBO 读回 RGBA 再 CSC 到 YUV | 多一次 RGBA 中转、同帧阻塞；除非要做去畸变等 GPU 处理否则不选 |

路线 A 的同构先例（可参考不可直接复用）：[`GalaxyHabComposition.kt:67`](../../galaxy/service/src/main/java/com/ecarx/autoservice/projection/GalaxyHabComposition.kt#L67) `ImageReader.newInstance(...,3,USAGE_CPU_READ_OFTEN or USAGE_GPU_COLOR_OUTPUT)`；`:199` `acquireLatestImage()`+`image.use{}`；`:213-217` 校验 `pixelStride`/`rowStride` 后逐行拷；`:224` 把 `copyTotalMicros/copyMaxMicros` 打进报表——**代价是被测量的，不是被声称的**。

代价量级【工程约定，仅设预期不作验收】：

| 形态 | 单帧 | 25fps 单路 | 四路合计 |
| --- | --- | --- | --- |
| YUV420 1080p | ≈3.11 MB | ≈78 MB/s | ≈311 MB/s |
| RGBA 1080p | ≈8.29 MB | ≈207 MB/s | ≈829 MB/s |
| 参考：现有 HAB 1920×532 RGBA | ≈4.09 MB | — | 单路 |

以上只是 memcpy 下限，不含 CSC、JNI 边界、plane 拆分与压缩本身。**四路软编＝要在 CPU 上搬 ≥311 MB/s 并同时压 4 路**，能否成立必须实测（§7）。

**为何不能假设四路并发软编可用**：① 软编吃 CPU，与 CarPlay 解码/投屏、Cluster 渲染、HAB 合成、车辆采集抢核，本项目历来要求整改前后 CPU/内存/线程/FD 对比而非静态推导（[AGENTS.md](../../AGENTS.md)）；② `getCapabilitiesForType(mime)` 给的是实例数**声明上限**，不是"四路 1080p25 满帧"的保证【平台】；③ 单实例内即多线程，四实例线程/内存/调度线性叠加，8155 散热降频未知（§7-9）；④ 因此默认拒绝，只在实测过的具体组合开放。

| 组合 | 处理 | 依据 |
| --- | --- | --- |
| 硬编+四路+跟随原生+25fps | **允许**（默认） | 硬编独立通路；仍需实测并发（§7-2） |
| 硬编+四路+HEVC | 允许，但必须展示"本机是否报告 HEVC 编码器"；未报告则置灰 | §1 探测；不得默认存在 |
| 硬编+四路+高档码率 | 允许，但须校验四路合计 ≤ 介质写入吞吐实测值 | §4.3；未实测只给自动档 |
| 软编+1 路 | 允许（实测通过后） | 单路成本可测 |
| 软编+2 路 | **显式告警**：写出实测 CPU 占用与是否掉帧；未实测则置灰 | §2 |
| 软编+3/4 路，或软编+1080p 以上+多路 | **必须拒绝**（置灰+"四路软件编码未在本车验证"） | 不做"先跑再崩"；§2 量级 |
| 选了软编但无软件编码器 | **拒绝创建**并报"本机未报告软件 H.264/HEVC 编码器"，**不得**回退硬编 | §1 |

## 3. 编码参数

**格式取舍**：H.264 默认（S-ENC-01 默认值），兼容性优先；H.265 仅在"探测到该实现 + 该路数实测通过"后开放，无 HEVC 编码器则置灰并写明原因。回放端在本机用 MediaCodec 解码，HEVC 需解码器支撑，而项目已有"无硬解时系统自选软解、低端车机跟不上"的判断（[`HevcSupport.kt:7-16`](../../common/src/main/java/com/shilapi/xcertplay/HevcSupport.kt#L7-L16)）；"编 4 路 + 解 4 路"压力叠加；HEVC 硬编实例数常少于 AVC 属**待核验**。**"H.265 一定更省空间"不得承诺。**

configure 前必须全部通过的校验【平台】：

| 参数 | 键 | 校验 | 失败即拒绝 |
| --- | --- | --- | --- |
| MIME | `KEY_MIME` | `supportedTypes` | 无该实现 |
| 尺寸 | `KEY_WIDTH/HEIGHT` | `VideoCapabilities.isSizeSupported(w,h)` | 超范围 |
| 帧率 | `KEY_FRAME_RATE` | `areSizeAndRateSupported(w,h,fps)` | 超范围 |
| 码率 | `KEY_BIT_RATE` | `getBitrateRange()` | 超范围 |
| 色彩格式/profile/level | `KEY_COLOR_FORMAT`、`KEY_PROFILE`/`KEY_LEVEL` | 前者须在 `colorFormats` 内；后者查 `profileLevels` | 软编无匹配 YUV，或组合不在 profileLevels |

同构参考：[`VideoDecoderCapabilities.kt:11-25`](../../galaxy/shared/src/main/java/com/shilapi/xcertplay/media/VideoDecoderCapabilities.kt#L11-L25) 把 `supportedWidths/supportedHeights/widthAlignment/fpsRange` 全打进日志——编码侧照做并把同样字段写进 P11。整体组合另用 `CodecCapabilities.isFormatSupported(format)` 复核。<https://developer.android.com/reference/android/media/MediaCodecInfo.VideoCapabilities>

**宽高对齐**：编码器只接受满足 `getWidthAlignment()/getHeightAlignment()` 的尺寸（常见 2 或 16，**必须读 API 而不是记数字**）。不满足时只能 **pad 补边**或**按对齐向下取整并 crop**，**禁止上采样放大**（spec §6）。P7 必须显示"请求 1920×1080 · 实际编码 1920×1088"这类真实值；若 crop，索引须保留有效区域矩形，回放/导出按原始视野处理。

**码率关系**【工程约定】：`bps ≈ bpp × W × H × fps`，bpp 经验 0.05–0.12。

| 组合 | 0.05 | 0.12 | 四路合计(bpp=0.08) |
| --- | --- | --- | --- |
| 1080p25 | ≈2.6 Mbps | ≈6.2 Mbps | ≈16.6 Mbps ≈2.1 MB/s |
| 720p25 | ≈1.2 Mbps | ≈2.8 Mbps | ≈7.4 Mbps ≈0.9 MB/s |

"自动"＝按公式算并夹到 `getBitrateRange()` 内，界面显示实际 bps（S-ENC-05）；低/中/高＝自动值 ±50% 内取档同样夹紧。四路合计须与介质写入吞吐实测值比较才放开高档，未实测只给自动档。

**GOP 与 seek**：拖动精度下限 ≈ GOP（seek 落到目标前最近 I 帧）。默认 1 秒＝25fps 每 25 帧一个 I、60 秒段约 60 个。`KEY_I_FRAME_INTERVAL` 单位是**秒**（int）；0.5 秒需与编码器支持核验；`0`＝仅首帧，**不可用于录像**。索引须记录实际 GOP 与关键帧 PTS（实际值可能被编码器修正）。

**MP4 封装**：一路一文件（`MediaMuxer(path, MUXER_OUTPUT_MPEG_4)` + 一个 `addTrack`），四路＝四个 MP4（合[需求稿 §7](需求与DeepSeek交接-20261103.md)）。【平台】`stop()` 才完成封装（含 moov），**未 stop 的文件不可播放**；不支持 faststart 重排、不支持追加已存在文件。构造有路径版与 FD 版（`MediaMuxer(FileDescriptor,int)`，API 26+，供 SAF 用）。`setOrientationHint` 只在确有旋转语义时用，**不得用它假装方向已处理**。文档：<https://developer.android.com/reference/android/media/MediaMuxer>

收尾顺序（不可交换）：①各编码器 `BUFFER_FLAG_END_OF_STREAM` →②drain 到 EOS 并把剩余帧 `writeSampleData` 写完 →③`muxer.stop()` →④`muxer.release()`/`encoder.stop()/release()` →⑤`fd.sync()`/`Os.fsync` →⑥`renameTo(最终名)` →⑦写索引转 COMPLETE。**用户主动停止也必须走①②③，不得跳过直接 `release()` 丢掉 moov。**

| 失败/取消 | 处理 |
| --- | --- |
| 编码器异常/某路断流 | 该路按 EOS 收尾；muxer 仍可写则留该路部分段标 `partial`（缺路时间范围必填），他路正常完成 |
| 写盘异常（满/IO） | 停止该段→`release()`→文件改名 `.partial`→报 WRITE_ERROR+原因→按 §4.4 判是否暂停 |
| 进程被杀/断电 | 停在 `.writing`，启动按 §4.7 恢复扫描判定 |

## 4. 存储

| 落点 | 取路径 | 权限 | 真实边界 |
| --- | --- | --- | --- |
| 内置 App 专属 | `getExternalFilesDir(null)`/`filesDir` | 无 | S-STOR-01 默认；与内置分区共享空间 |
| U 盘 App 专属 | `getExternalFilesDirs(null)` **下标≥1** | 无 | 可写无需 SAF；**随卷移除即不可访问** |
| U 盘根目录/用户可见 | SAF `ACTION_OPEN_DOCUMENT_TREE`+`takePersistableUriPermission` | 用户授权 | 才需要 SAF；`MediaMuxer` 只能用 `openFileDescriptor(uri,"rw")` 得到的 FD |

**"是否必须 SAF"**：AutoRecord 自己录/回放/导出**不需要** SAF，App 专属目录足够；只有"让用户用文件管理器直接看到"或"导出到用户选定目录"才需要。故 S-STOR-01 的"内置/各 U 盘卷"两档不依赖 SAF。既有用法：`getExternalFilesDir(null)` 见 [`GalaxyStorageUsage.kt:12`](../../galaxy/common/src/main/java/com/shilapi/xcertplay/GalaxyStorageUsage.kt#L12)、[`DiagnosticExportStore.kt:58`](../../common/src/main/java/com/shilapi/xcertplay/DiagnosticExportStore.kt#L58)。

卷枚举与判别：

```kotlin
val volumes = context.getSystemService(StorageManager::class.java).storageVolumes  // API 24+
volumes.filter { it.isRemovable() }.forEach { v ->
    val state = v.state; val uuid = v.uuid; val label = v.getDescription(context)
    val dir = if (Build.VERSION.SDK_INT >= 30) v.directory else null  // getDirectory 是 API 30
}
```

- 【平台】`StorageVolume.getDirectory()` 是 **API 30**（本机恰好可用，但仓库 `minSdk=29` 必须带版本判断，如 [`galaxy/cluster/build.gradle.kts:5`](../../galaxy/cluster/build.gradle.kts#L5)）；文档 <https://developer.android.com/reference/android/os/storage/StorageVolume>
- **持久化存 `uuid`，绝不存绝对路径**（挂载点与 `externalFilesDirs` 下标都会变）；解析不到＝**已移除**，必须报"卷已移除"，**不得**静默回切内置。剩余用 `File.getUsableSpace()`（先例 [`GalaxyUpdateTransfer.kt:55`](../../galaxy/common/src/main/java/com/shilapi/xcertplay/GalaxyUpdateTransfer.kt#L55)：目标大小+4 MB 余量）；需块级细节用 `StatFs(path).availableBytes`。【平台】
- `externalFilesDirs` 下标 0 恒为主存储，下标≥1 属可移除卷，但**下标顺序与 `storageVolumes` 顺序不保证一致**：必须用 `volume.directory` 与候选目录 `canonicalPath` 前缀匹配绑定，不能靠序号猜。
- 两层阈值：绝对下限 S-STOR-04（默认 2 GB）与下一段预留（§3.4 四路码率×分段时长×1.2）。**每段开始前重查**，不能只在开录时查一次。

配额与循环覆盖的判定顺序（顺序即优先级）：

```
① 卷状态 == MOUNTED          否→REMOVED/READ_ONLY，暂停录制
② 目标目录可写探测(.probe)    否→WRITE_ERROR（权限/只读卷/坏盘）
③ 剩余 ≥ S-STOR-04 绝对下限   否→LOW_SPACE，暂停录制
④ 剩余 ≥ 下一段预估；且 已用+预估 ≤ S-STOR-02 配额    否→需腾空间
⑤ 腾空间：S-STOR-03 覆盖开 → 删最旧且未锁定/未在写/未导出的段
            覆盖关 → FULL，暂停并提示"请删除或换介质"
⑥ 删后重跑③④，仍不足→FULL 并显式报原因
筛选：锁定段永久跳过；正在写入段跳过；正在导出段跳过（引用计数）
```

"最旧优先"先例：[`GalaxyLogRetention.kt:22-33`](../../galaxy/common/src/main/java/com/shilapi/xcertplay/GalaxyLogRetention.kt#L22-L33)。**禁止**自动格式化、删用户其他文件、U 盘失效后静默换目录（[需求稿 R09](需求与DeepSeek交接-20261103.md)）。

必须显式报出的状态：`OK`｜`LOW_SPACE`（剩余<下限+录制暂停）｜`FULL`（配额满且不可覆盖）｜`READ_ONLY`（报卷名+"只读"）｜`REMOVED`（报"U 盘已拔出（卷名）"+暂停，**不换介质**）｜`WRITE_ERROR`（errno/异常类型+卷名+路径）｜`IO_ERROR`（"该段写入失败"+段 ID+保留为 partial）｜`THROTTLED`（实测 MB/s 与需求值）。

写盘事务：**写完 → 先 fsync → 再 rename → 最后写索引**。理由：rename 是同卷原子操作，是"这段数据存在"的提交点；先 rename 后写索引只会产生"索引缺但文件在"的孤儿（可扫描恢复），反序则产生"索引指向不存在文件"的坏条目；fsync 必须在 rename 前，否则 rename 可能先落盘得到"名字正确内容为零"；`muxer.stop()` 必须在 fsync 前（moov 没写完 sync 是白 sync）；索引自身也要 tmp+fsync+rename 或 SQLite 事务。同纪律先例：[`GalaxyUpdateCache.kt:20-23`](../../galaxy/common/src/main/java/com/shilapi/xcertplay/GalaxyUpdateCache.kt#L20-L23)（`fd.sync()`→`renameTo`）、[`GalaxyUpdateTransfer.kt:94`](../../galaxy/common/src/main/java/com/shilapi/xcertplay/GalaxyUpdateTransfer.kt#L94)（rename 作提交点）、[`LocalMfiIdentityStore.kt:126`](../../galaxy/shared/src/main/java/com/shilapi/xcertplay/mfi/LocalMfiIdentityStore.kt#L126)。

断电恢复扫描：①扫 `*.writing`/`*.partial`；②用 `MediaExtractor.setDataSource` 探 track 数——可读（moov 完整）→收编为 RECOVERED，**不冒充完整**；不可读→PARTIAL，列"时长未知/尾部截断"，可给"尝试修复"入口但默认不进完整列表；③有完整文件无索引（孤儿）→从 sidecar/文件名重建，标 REBUILT；④索引引用但文件缺失→标 MISSING，不自动删，报用户。【平台】`MediaMuxer` 无续写/修复能力，能否读出取决于 moov 是否落盘，故只能用 `MediaExtractor` 探测。**"能读出来"≠"四路同步完好"**，缺路与首帧差仍按 §5 记录。

## 5. 分段与统一会话时钟

- 一个 segment＝四路+车辆样本+事件+缩略图，按**统一会话时间**切段，不是各路自己数满 60 秒帧。索引与 sidecar 记 `startTimeUs/endTimeUs`，四路实际覆盖范围分别记（允许某路短于段窗口）。段首帧需强制 I 帧（重建编码器或 `KEY_REQUEST_SYNC_FRAME`），**切段开销要计入**。
- **PTS 必须来自真实帧时间**：允许生产端 buffer 时间戳（§2）、`ImageReader` image timestamp、相机时间戳经映射的单调时间；**禁止 `帧序号 × 固定时长`**（上游 EVCam 的 `帧号×40000µs` 正是此类，见[需求稿 §8](需求与DeepSeek交接-20261103.md)，本项目不移植——掉帧时凭空造出没有画面的时间并与车辆历史漂移）。代码红线：时间只能取自帧元数据字段，不允许出现"index*常数"作为时间来源。
- **首帧时间差必须记录且不得归零**：`segment.startUs`；每路 `firstFrameUs`（与 startUs 之差如实保留）、`lastFrameUs`、`gapRanges`、`frameCount`/`droppedEstimate` 及依据。回放按每路自身首帧偏移对齐；掉帧/迟到**不补帧、不重排、不拉伸**，编码出帧时间与喂帧时间都记，以区分"摄像头没给"与"编码器丢"。
- **时钟锚点**：段内用单调时钟排序计时；会话开始记 `clockEpoch{monotonicNs, wallClockMs, timezone, sessionId}`；墙钟回拨不改段内顺序只影响显示；重启＝新 epoch/新会话，**不跨 epoch 拼时间轴**。【源码】契约已有时间语义基础：`VehicleSignal` 的 `receivedAt/sourceTimestamp/epoch/maxAgeMillis`（[`VehicleSignal.kt:9-18`](../../galaxy/contracts/src/main/java/com/galaxy/auto/contract/VehicleSignal.kt#L9-L18)），视频侧与车辆侧共用同一时间轴。

## 6. 目录结构与旁路数据格式

```
<root>/AutoRecord/
  index/index.db                        # SQLite 索引（缓存式，可重建；重建经 index.db.tmp）
  segments/20261103/20261103-215300-<segId>/
      front.mp4 rear.mp4 left.mp4 right.mp4   # 四路独立；写入中为 <name>.mp4.writing
      vehicles.jsonl  events.json  segment.json  thumb.jpg
  tmp/                                  # 导出临时，启动清理
```

**结论：sidecar 是真相，SQLite 是索引，两者都要。** 纯库存样本的缺点：样本 250–1000 ms/次高频写、进程被杀时库更脆弱、导出要带数据库；纯文本缺点：跨段筛选/分页/事件检索要全扫。采用分工：库只放段/轨/事件可查询元数据+路径+完整性+引用计数；**原始车辆样本只进 `vehicles.jsonl`**（[需求稿 §7](需求与DeepSeek交接-20261103.md)：原始样本属用户录像数据，不得写诊断日志），每行一条样本、字段对齐 `VehicleSignal`、只追加不重写、断电最多丢尾行（读时丢弃不可解析尾行）；`events.json` 存 eventId/type/start/end/source epoch+seq/触发样本引用/规则版本/精度；`segment.json` 是该段自描述清单（schemaVersion、四路文件与实际编码器名/profile/level/实际码率/GOP、时间范围与首帧差、缺路区间、样本/事件数、缩略图引用）——**单段目录拷走即可被理解与导出**。升级路径：全部带 `schemaVersion`，只增不改语义；index.db 版本不符**直接重建**（来源是 sidecar），索引损坏≠数据丢失。缩略图从已编码文件或预览帧取，**不额外开一路采集**（[需求稿 R12](需求与DeepSeek交接-20261103.md)）。

## 9. 设置页必须如实展示 / 禁止承诺

**必须如实展示（每项须有运行时来源，不能写死文案）**：① 将使用的**实际编码器名**（create 后回读 `codec.name`）；② 该编码器**硬/软/未知**三态；③ **实际编码尺寸**（含对齐后真实值）与请求差异；④ **实际配置码率 bps** 与四路合计；⑤ **实际 GOP** 及其对拖动精度的影响；⑥ **实际帧率**（出帧数÷时长，非设定值）；⑦ 卷名+剩余/总量+卷状态（按 uuid 解析实时反映）；⑧ 配额与实际已用+"循环覆盖将删最旧未锁定段"提示；⑨ **四路并发实测状态**（发起 N/成功 M/最近失败原因与阶段）；⑩ **"下一段生效"**提示（改动不打断当前段）；⑪ 软编选项旁写明"需自取 YUV、代价更高、可用路数由实测决定"。

**禁止承诺（文案红线）**：① 禁"软件编码一定可用"/"四路软编可用"；② 禁把"H.265 更省空间"当既定结论；③ 禁把"U 盘可写"当静态结论，只能展示**探测结果**；④ 禁"断电不丢录像"；⑤ 禁把"编码器创建成功"显示成"录制成功"——只认**出帧+写盘+段 rename 完成**（spec §2 P1）；⑥ 禁把"清单里有 4 个硬件编码器"说成"支持四路"；⑦ 未实测时不得把任何分辨率/帧率/码率组合标为"推荐/已验证"。
