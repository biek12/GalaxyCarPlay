## 2. Camera2 设备枚举

`dumpsys media.camera`：`Number of camera devices: 52`，`Device N maps to "N"`，52 台的特性**完全一致**（API1 `Facing: Back`、pixelArray 3280×2464、fps 1–25、`LIMITED`、`Conflicting devices: None`）。

`/dev/video51…video58` 只有 8 个节点；平台为 Qualcomm AIS（`ro.hardware.camera=ais`、`init.svc.qcarcam_hal`、`init.svc.vendor.camera-provider-2-4`）。⇒ 52 个 Camera2 ID 是厂商 HAL 合成的虚拟视图，物理输入远少于 52。

**逐 ID 实开结果（52 台全部尝试）**：

| cameraId | 结果 |
| --- | --- |
| 0、1、2、3 | 出帧成功，四路画面互不相同（md5 各异） |
| 51 | 出帧成功，但画面与 ID 2 是**同一视角**（同车位线、同车列、同灯位）→ 同一物理相机的别名 |
| 4–50 | `IllegalArgumentException: connectHelper:1734: Illegal argument to HAL module for camera "N"` |

HAL 日志同时出现 4 条独立流：`qcarcam_start [0..3]`，与 0–3 四路一一对应，且关闭时各自 `qcarcam_stop`。

## 3. 实测能力参数（真实开流，非 dumpsys 推断）

| 参数 | 实测值 | 备注 |
| --- | --- | --- |
| JPEG 输出尺寸 | **仅 1280×800** | `jpeg_sizes` 单值；dumpsys 报的 3280×2464 不是本路径的 JPEG 输出 |
| 帧率范围 | 1–25 fps | `[[1,25]]` |
| hardware level | `0`（LIMITED） | 2026-11-04 按本机 SDK 常量纠正旧 LEGACY 解释；LEGACY 的值是 2，具体输出仍以实开为准 |
| `LENS_FACING` | 全部 `1`（FRONT） | 厂商把车外四路统一标成 FRONT，**不能用 facing 判方向** |
| `SENSOR_ORIENTATION` | 全部 `0` | 无旋转，横屏 800×1280 输出 |
| 返回缓冲区 | 固定 6 000 000 字节 | 与 `android.jpeg.maxSize` 同值；真实 JPEG 需按 EOI(`FFD9`) 截断 |
| 解出的 JPEG 头 | `ffd8ffe1` | 含 EXIF，可直接解码 |
| Vendor tags | `configured vendor tag descriptors: None set` | HAL 不提供方位/视图名字段 |

## 5. 画面与方位

四张图见 `docs/AutoRecord/assets-20261103/`（`q640_0..3.jpg`，`quad_montage.jpg` 为 2×2 拼图，`prev_51.jpg` 为 51 号同视角对照）。

**已确认**：0/1/2/3 是四个不同视角（构图、地面标线、自身车身位置各不相同）。

**未确认：哪一路是前/后/左/右。** 两个候选假设互相冲突，本轮无法用像素证据排除：

- 假设 A（EVCam 位置序）：`0=左、1=右、2=前、3=后`（来源：上游固定提交 `0876b97` 的 `initCamerasForL7` 按 `cameraIds` 位置装配）。
- 假设 B（现场几何）：本轮为夜间停车场，ID3 正面是绿篱/路缘/隔离柱（像车头朝向障碍），ID2 是开阔场地（像车尾朝外），ID0/ID1 均含近距离白色车辆（像左右邻车）。

两者对 2/3 的判断正好相反。判定需要**地面真值**：有人在车前/车后分别走动一次，或把车移位后各拍一张；届时按 md5 与画面内容对号即可。

## 6. 局限与未知

- 只验证了**单帧抓拍**，未验证持续 25 fps 长时推流下的掉帧、温度、与原生 360/倒车影像的共存抢占。
- 未验证 AutoRecord 需要的编码路径（MediaCodec 输入 Surface）、四路长时间并发资源占用。
- 方位未标定（见 §5）；`sensor_orientation=0` 与 `facing=FRONT` 都不能代替标定。
- 抓拍期间原厂环视未被主动调用，本轮无法证明「原厂占用时能否抢占/被抢占」的真实行为。
- 用户车的实际车位朝向本轮未由用户现场确认，几何推断仅为假设 B。

## 7. 对 AutoRecord 的重建建议

1. **方向表必须可配置**，按 `cameraId → 方位` 落地，默认先写假设 A，标定后改数据不改代码（与既有「AutoService 枚举并在目标 L6 标定方向，不照抄 E5 默认值」一致）。
2. **只认 0–3**，并对 51 做去重：打开前按 `(id 集合 ∩ 实开成功集合)` 处理，避免把别名当第五路。失败 ID 的 HAL 异常文案原样记录，作为「缺路」证据而不是静默跳过。
3. **取帧必须按 EOI 截断**：缓冲区恒为 6 MB，直接落盘会写 6 MB 垃圾；截断后典型 0.55–0.83 MB。
4. **不要依赖 CameraCharacteristics 判断方位或能力上限**：facing 恒 FRONT、dumpsys 尺寸与实际 JPEG 尺寸不一致，能力必须以实际 `getOutputSizes(ImageFormat.JPEG)` 为准。
5. **四路并发可按「并发发起、各自等待」实现**（本轮验证可行），但 HARWARE LEVEL=LEGACY，不要假设支持 REQUEST 模板级的高级控制；AE 之外的模式本轮未验证。
6. 传输/展示层建议直接消费 1280×800；四宫格缩略图在端上再做缩放，不要把 6 MB 缓冲跨进程搬。
