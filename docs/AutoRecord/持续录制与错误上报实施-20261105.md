# 持续录制与错误上报实施

本轮用户要求执行连续录制方案，在隔离模拟器持续录制，循环配额固定1G，并增加四个自有App错误与崩溃恢复上报。2026-11-05继续，车辆未连接；用户另行补充SSH密钥用于自有服务器更新。

## 实现与验证范围

- 普通换段保持Camera2/Reader/MediaCodec；连续编码包以有界队列进入单写线程，muxer/事务只由此线程持有。旧段封装、fsync/rename、缩略图期间编码继续；不为下一段再开第二组编码器。包队列最多256项/24MiB，超限具名停止并保留失败证据，不无限堆积。
- 整分计划由一次墙钟/单调时钟锚点映射；首段12:15:46→12:17:00，后续60秒。实际MP4从真实关键帧开始，所有帧PTS不重写为伪造时刻；`continuity.json`记录计划边界和各路首尾源PTS。关键帧迟到超过一段时继续保存已有输出、记录异常，不为补齐文件名丢弃画面。源帧时间触发关键帧请求，减少引擎UI调度的影响。
- 分段/删除后刷新实际配额账本，包写入仅扣减字节，每秒回读介质空闲，结合下一段与8MiB封装/侧录预留，循环覆盖只删自有未锁/非事件保护且不在写的段。存储卷剩余空间每次实际回读，不沿用启动时的旧值。
- 测试采用两类源：实际Camera2连续短段；高熵合成YUV经真实ImageWriter→ImageReader→MediaCodec→MP4长录。后者为加快真实1GiB配额循环覆盖，不代表车辆画面、硬件编码性能或四路并发能力。不用填充文件伪造写满。
- 错误持久化进入来源App本地outbox，经签名权限/UID核对的AutoService inbox集中收取，ACK后才删除；自有服务器再ACK后才清理中继。错误上传与12/24小时远程Shell授权分离，自动运行/诊断上传关闭则停止出网；缺少私有登记材料不连接公网。
- Java崩溃现场只同步本地留证，委托原崩溃处理器；原生SIGSEGV/ANR等由App恢复后读取系统退出记录补报。系统未提供trace必须明确not_available，不能编造根因；异常类、脱敏message、源码栈、cause/suppressed、来源App/版本/进程、调用操作、允许字段的参数与退出状态一同记录。未知参数只上传类型，认证材料、任意Shell正文、录像、车辆载荷不上传。
- 各队列/服务端保留有界；App最多128条/2MiB，中继8MiB；服务端每设备最多1024条/64MiB/30天。达到容量的淘汰/拒绝与原生证据缺失是实际限制，不承诺无限“完整”。重复事件ID幂等，冲突拒绝。

### 高熵压力源的失败与修正

前两轮纯8位白噪声在软件编码器首帧失败，没有进入长录；保留测试失败和日志。24Mbps一轮超出声明上限；8Mbps一轮虽在`[1,20000000]`范围内仍失败。完整模拟器日志给出`SoftAVCEnc: Encode Frame failed = 0x283`，其低8位`0x83`在固定Android11 libavc源码中为`IH264E_BITSTREAM_BUFFER_OVERFLOW`（[ih264e_error.h](https://android.googlesource.com/platform/external/libavc/+/4631339e9289594e2fcfa1af1bab1565ad72c162/encoder/ih264e_error.h#80)）。这是模拟器软件编码器对该极端压力源的具体失败，不把首次异常全归为码率，也不外推车辆硬件编码器有同一缺陷。

后续压力源明确改为每帧变化的4位亮度/5位色度量化噪声，12Mbps、1280×720×20fps，仍需真实编码并超过1GiB触发循环覆盖。参数和场景写入测试结果；不是生产静默降码率或复制/填充文件。

### 00:28 压力源烟测

4/5位逐像素量化噪声仍触发软件编码器首帧溢出；进一步明确为每帧变化的2×2亮度块（4位）、中性色度，12Mbps，实测10秒编码34,386,510字节，193入帧/193输出、背压0，两个实际分段均成功提交，边界源PTS差45,072us。该结果仅为SMOKE_ONLY，不是1GiB覆盖验收。由于实际码率高于请求值，循环配额必须按真实文件字节结算，不能仅凭设置码率估算。

30分钟1GiB实写覆盖测试随后启动，最终结果待追加。App CPU单独统计不含运行在media进程的软件编码CPU，额外保留系统cpuinfo快照；不能把App占用当整条编码链总占用。

### 诊断构建来源补充

四App的版本号目前可能相同，不能单凭0.1.0识别构建。公共日志初始化在后台计算实际base APK的SHA-256，事件包含`apkSha256`；恢复事件另记录可匹配上一进程的`crashedApkSha256/crashedVersion`，与当前负责补报的版本区分。没有旧构建记录、首次启动尚未算完摘要或不能匹配的系统历史退出明确为unknown/unavailable，不猜测来源。摘要读取失败不阻止退出恢复/本地队列发送。

Binder连接、绑定、权限申请、调用以及服务端排队执行的异常均接入公共报告，保留实际异常链与来源包；CAMERA等权限仍遵守原签名/UID和授权屏障，没有为了日志上报扩大相机或车辆访问。AutoService上传worker固定一个休眠调度线程，避免延迟队列配合核心超时造成反复销毁/重建线程。

### 26分钟发现的输入丢弃边界

第二轮前20分钟生产/输入/输出一致；约第26分钟累计出现13个输入缓冲等待超过20ms的帧被放弃。该轮即便覆盖与文件验证通过，也不算帧完整性通过。必须保留此发现，不把前半程0丢帧外推全程。

最终输入策略改为持有已借出的图像，在有限Reader队列内阻塞等待缓冲；20ms只是一次等待粒度，不再作为丢弃阈值。生产端通过原生BufferQueue承压，不建立无界帧副本队列；连续8秒得不到缓冲报具名错误。主动停止先发stopInput取消等待，再进入图像归还/关闭屏障，避免等待同锁死锁；native释放仍由唯一drain所有者完成。新的测试在收尾排空后强制核对生产帧＝编码输入＝编码输出＝实际MP4样本总数，并单独统计暂态等待次数，重新执行完整30分钟。

### 原生崩溃上下文与中继幂等补强

Android11退出接口可能只给reason=5而不给可用原生trace。AutoService接收恢复事件时，在已有READ_LOGS授权下可补读crash缓冲中**相同App、相同PID、故障时窗**的signal/backtrace；只保留调用栈，不保留寄存器、内存dump或其他App日志。没有权限、缓冲已滚动或超时都明确标记不可得，不编造调用链。解析边界有独立测试，实际SIGSEGV注入验收待长录结束后执行；这与此前Java崩溃补报分别记账。

服务器修正ACK丢失后的重投语义：来源事件相同、仅中继receivedAt/sourceUid/nativeTrace上下文变化时继续ACK，不会因重收时间变化而409卡住队列；来源事件本身变化仍拒绝冲突。已通过新增竞态回归并再次部署自有服务。

### 日志容量边界复核

系统trace按UTF-8字节限制，过大的异常链/参数/trace明确标记truncated后再入队，避免单条超过服务端64KiB上限后堵住队列。来源outbox按“已有字节＋待写字节”执行2MiB上限；AutoService inbox按补充native上下文后的实际序列化字节执行8MiB上限。此项不影响正在长录的四个编码/写盘核心文件，重建与诊断注入在长录结束后进行。

原生补报复现入口：`bash scripts/test_native_diagnostics_emulator.sh`，只允许固定AutoRecord_Offline模拟器，给自有服务测试READ_LOGS后注入自有AutoRecord Java异常与SIGSEGV；不连接车辆，不调用公网。

## 追加：用户要求崩溃后自拉起（实施中）

用户继续要求崩溃后自动拉起。本轮将录制会话迁至`RecordSessionHub`（Application上下文）及`RecordSessionService`（camera类型FGS），UI仅观察快照、借用预览Surface，不持有编码器/录制车辆订阅。回到桌面或销毁页面不结束已允许后台的录制；活跃录制期间持有PARTIAL_WAKE_LOCK，正常收尾后释放，不用于唤醒已休眠的车机。

恢复使用两层：系统START_STICKY，以及进程存活时预先登记的非唤醒ELAPSED_REALTIME恢复闹钟（10秒心跳推迟30秒期限）；Java未捕获异常同步本地留证后将恢复期限提前至3秒起步，连续失败退避至最多60秒，不擅自关闭用户功能。原生崩溃不能运行Java handler，但已登记PendingIntent留在系统中。恢复代次与持久wanted先校验；主动停止同步清除wanted并撤销闹钟，迟到旧代次也不能重启。AutoService沿用automatic开关、原有15分钟Job与Sticky，增加同一快速恢复机制。

AutoRecord录制设置增加`recoverAfterCrash`实现默认true（用户本轮要求自动恢复），可关闭；开机/启动自动录制仍保持既有默认false，不伪称用户确认了开启默认值。恢复沿用上次明确选定方向/介质/编码设置，不静默减少方向或切换编码。上次会话的writing清单固化为failed并附previous_process_exit元数据，原始`.writing`字节原样保留，不伪造可播MP4；更早排查报告中的残留不因本机制被改写。

`SurfaceCameraSource`所需方向改为预览方向与实际recordSurface方向的并集；切单路预览/隐藏预览不再关闭其他正在录制的方向。通知更新按状态/段号变化发送，不在每100ms进度回调反复通知；App内真实录制徽标采用绿色。系统状态栏小图标最终着色仍由系统UI决定；屏幕边缘悬浮图标尚未实现。

Android11 camera前台服务需声明类型，后台新启动相机存在while-in-use限制，不能只凭CAMERA已授予断言后台可用。使用[官方Android11说明](https://developer.android.com/about/versions/11/privacy/foreground-services)及[系统启动的豁免说明](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)核对，并以模拟器真正后台重建后的Camera2写盘为验收，不用服务进程出现代替相机恢复。更高Android版本/指定L6仍分别验证。

测试入口`python3 scripts/test_record_recovery_emulator.py`只允许固定AutoRecord_Offline AVD；控制receiver仅存在于emulator APK并需shell的DUMP权限，Debug/Field产品APK没有该组件。测试启用的单路1280×720/软件编码/4秒片段均是显式模拟器夹具，不是产品兜底。最终注入结果待追加。
