# AutoRecord 录制闪退排查报告

排查日期：2026-11-04（北京时间）。指定车辆：银河 L6 2023 Max / FlymeAuto 2.3.1 / Android 11、arm64。

## 1. 结论

**已证实两次闪退均为录制取帧线程的原生非法内存访问（SIGSEGV），发生在自动换段收尾期间。高置信根因为：换段线程关闭 ImageReader 时，取帧线程仍在读取该 Reader 借出的图像平面，造成已失效内存被继续访问。**

这不是只凭源码推测：系统退出记录、两份 tombstone 的崩溃线程与引擎线程、车上实际 APK 的实现、段目录残留四类证据能够相互对应。尚未通过逐次内存释放追踪或受控复现证明故障地址的确切释放时刻，因此“内存所有权竞争”为高置信根因判定，不能写成修复已验收。

本轮按用户要求只排查、形成报告。通过既有 Android Root Telnet 读取历史证据，没有点击开始/停止录制、安装或重启应用、改动业务代码，没有电脑远程 ADB、原厂 HMI 或车辆控制操作。没有为复现而再次触发崩溃。

## 3. 两次故障实证

| 发生时间 | 进程 / 崩溃线程 | 系统记录 | 同时刻引擎线程 |
| --- | --- | --- | --- |
| 19:50:40.999 | PID2092，TID2212，`record-frames-3` | `SIGSEGV / SEGV_MAPERR`；exit-info于19:50:43.857记录 reason=5、status=11 | `rollover → stopSegmentOnHandler → ChannelEncoder.finish → LinkedBlockingQueue.poll` |
| 19:52:51.669 | PID9080，TID9119，`record-frames-1` | `SIGSEGV / SEGV_MAPERR`；exit-info于19:52:54.674记录 reason=5、status=11 | `rollover → stopSegmentOnHandler → SegmentTransaction.commitChannel → AtomicFiles.commitVideo → rename` |

两次崩溃栈的核心路径一致：

```text
ImageReader.ListenerHandler.handleMessage
  → RecordingEngine.startSegmentOnHandler$lambda$12
    → ChannelEncoder.queueYuv
      → ChannelEncoder.Companion.copyPlanes
        → java.nio.DirectByteBuffer.get
          → SIGSEGV (SEGV_MAPERR)
```

现场 tombstone 为 `/data/tombstones/tombstone_23`、`tombstone_24`；本机保存相关线程摘录。第二次补取了完整引擎业务调用链，确认不是仅凭“约一分钟”推断自动换段。

**这些退出不是同包更新造成的正常进程停止。** exit-info 中19:19、19:22等安装退出是 reason=10、`installPackageLI`；19:50和19:52明确是 reason=5。没有证据支持将这两次归为 Java OutOfMemory、系统低内存回收、ANR 或 AutoService 远程连接异常。这里只解释这两次已取得证据的事件，不否定历史上存在其他故障。

## 4. 根因链：为什么录着录着会退出

已装 APK 的反编译确认：

1. 每路在 `record-frames-*` 线程中 `acquireLatestImage()`，随后将图像同步传入 `queueYuv()`。`copyPlanes()`持有图像 Plane 的 DirectByteBuffer，逐像素读取源缓冲。
2. 到达片段时长后，`record-engine` 执行 `rollover → stopSegmentOnHandler`。
3. 引擎调用 `bindRecordSurface(..., null)`，但该接口向相机线程 `handler.post`，调用返回不代表旧会话已经释放。
4. 引擎只等待固定300ms，随后取消监听并调用各路 `ImageReader.close()`，**没有与取帧回调的“取帧→读取→归还”建立互斥或完成屏障**。取消监听也不能证明已进入回调的拷贝已结束。
5. 已经取得的 DirectByteBuffer 不会因为编码器的 `inputLock` 自动得到保护：该锁约束编码器输入及编码器释放，关闭 ImageReader 的线程没有持有同一把所有权锁。
6. 因而取帧线程可能仍在读源图像，另一线程已关闭 Reader。两次实际崩溃都发生在源缓冲 `DirectByteBuffer.get`，且同时刻引擎已进入 Reader 关闭之后的编码收尾/文件提交阶段。

Android 官方契约明确：关闭 ImageReader 后，继续读取此前 Image Plane 返回的 ByteBuffer 属于未定义行为；并不保证一定抛出可捕获的 Java 异常。[ImageReader.close 官方说明](https://developer.android.com/reference/android/media/ImageReader#close())

所以，增加 `try/catch`、只吞掉 `IllegalStateException`、延长等待或提高网络超时，都不能消除本次内存所有权竞争。原生 SIGSEGV 会终止整个进程，普通 Kotlin/Java 异常捕获无法保住录制。

## 7. 后续修复与验收建议（本轮未执行）
