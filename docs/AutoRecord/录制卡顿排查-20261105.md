# AutoRecord 录制卡顿排查（2026-11-05）

用户反馈开启录制后卡顿。本轮沿既有 AutoService HTTPS 远程通道采集本 App 日志、线程栈、CPU、编码统计及片段清单，并以工程原签名更新 AutoRecord。没有连接电脑远程 ADB，没有恢复本地模拟器测试，没有操作原厂 HMI、启动项或车辆控制。

## 实测原因

1. 原版本首次换段后出现 `record_writer_queue_exhausted`，异常链为单写线程队列 256 项满后 `RejectedExecutionException`，四路录制随后停止。采样时主线程处于正常消息等待，未发现主线程死锁证据。
2. 原版旧段四路 MP4 stop/release、fsync、清单及缩略图均阻塞新包写线程。第一段四路 MP4 文件提交到缩略图完成约 2.6 秒，四路共用的 256 包仅覆盖约 2.6 秒的 4×25fps 输入。
3. 单独拆分收尾线程后仍复现。09:32:06 的本 App SIGQUIT 线程栈进一步确认 `record-writer → prepare → RotationJanitor.makeRoom → SegmentScanner.scan → File.length/stat`：每次准备下一段重新扫描全部历史目录；收尾线程此时已空闲。不能把这一轮继续溢出归因于缩略图或宣称首次补丁已修复。
4. 四个 `record-frames-*` 线程两次 top 合计约 165%/161% CPU（100%=一个核心）。原来对交错 UV 使用 DirectByteBuffer 逐像素 get/put，累计拷贝统计每路约 37–40ms/帧。实车布局：源 `1280:1/1280:2/1280:2`，编码器目标 `1280:1/640:1/640:1`，编码器为四路 `c2.qti.avc.encoder`、1280×800、配置 25fps。
5. 另一次恢复录制中，初始化编码器/存储耗时计入 8 秒首次出帧看门狗，采集刚启动就误报超时；已将起算点移到采集绑定完成。

当时录像目录 28 段、约 1005MiB，介质剩余约 28GiB，不能将此次停录写成磁盘已满。

## 实施

- `recording/ChannelEncoder.kt:315`：每个取帧线程复用两行堆数组；直接内存批量读写，UV 拆分在数组中执行。目标为交错平面时保留另一色度分量，连续 Y 快路径保留。
- `recording/ContinuousSegmentWriter.kt:25`：队列包数按通道计（四路 1024），总编码数据仍硬限制 24MiB；停止控制任务可等待队列位置，避免数据队列满时连收尾都提交失败。
- `recording/ContinuousSegmentWriter.kt:110` 与 `storage/SegmentTransaction.kt:111`：旧段全部通道跨界后显式移交唯一收尾线程；新段继续写入。收尾窗口最多两段；循环删除排除正在收尾的目录。
- `recording/ContinuousSegmentWriter.kt:132`：首次建立实际空间账本，之后按真实编码字节扣减；正常换段不扫描全库。预算不足才扫描并按既有锁定/事件保护规则覆盖，每秒仍检查介质实际剩余空间。接近配额时的扫描仍需专门长录验证，不声称所有容量下恒定延迟。
- 移除录制链路中旧单路 `thumb.jpg` 解码；录像库原有 `ui/RecordThumbnail.kt` 继续按需生成真实四向缩略图。
- `recording/RecordingEngine.kt:81`：首次出帧超时从采集绑定完成后起算；新增私有 Service dump 输出队列、阶段、输入/输出/丢弃与拷贝耗时，用于现场对比。
