# QNX接收端按投屏需求自动唤起

2026-10-30。用户要求：有仪表投屏需求时，AutoService必须主动唤起已退出的接收端；QNX重启后同样自动恢复，不能依赖用户进入诊断页。该要求已落实到源码和本机回归，新包尚未安装或实车验收。

## 运行流程

“接收端有限监听会退出”描述的是接收进程自身的生命周期，不代表以后只能人工启动。上一版已有直连失败后自动准备的分支；本次补齐立即请求Root恢复、复用持久安装和重启后PID处理。

```text
CarPlay / AutoCluster / 其他契约客户端提出实际投屏需求
  → 尝试现有HAB接收端（普通App，失败再用现存UID0 helper）
  → 可连：保留原发送会话直接投屏
  → 不可连：主动请求接收端唤起
      → Root未就绪：提前执行等待中的恢复；正在恢复则共用本轮
      → UID0 helper自动取得已核验来源的QNX认证并登录、读回QNX UID0
      → 接收端正在监听且文件匹配：复用
      → 已退出 / QNX重启，文件和owner key匹配：校验后直接启动
      → 首次 / 程序或owner key变更：部署、校验后启动
      → 确认监听，再完成HAB AUTH / INIT / ACK，继续同一投屏需求
```

“唤起”在接收端不运行时需要QNX控制连接；仅向HAB发数据不能让不存在的进程执行。这个连接和登录由AutoService自动处理，正常使用无需手工开Root、找密钥、导入文件或点诊断按钮。现有直连可用时仍不等这条准备链。

没有投屏消费者时不创建QNX唤起任务；消费者正常停止后由HAB STOP释放自有窗口/共享区，接收程序回到原有有限监听。下一次需求在它退出后仍会重新唤起。本次未改原车启动项/HMI，也没有为待机建立额外永久轮询。基础恢复仍按原设计独立维护；持续失败按现有有界退避恢复，主动停止会使旧回调失效。
