# EVCC 3.3.3：流畅度、动态调度与主题样式补充

> 后续实施更新（2026-10-30）：本文保留前一研究/优化阶段的原始证据。当前已实现可视化编辑器、24类/72预设、日夜/组件覆盖、EGL合成、可配置按内容刷新及自有GLC2消费确认；删除原100ms采集/主题轮询上限。当前源码与准确入口见[实施方案](Cluster可视化主题编辑器实施方案-20261030.md)，验证见[上车验收](Cluster上车验收-20261030.md)。实际显示帧率、8155负载与原车告警仍未实车验收。下文“当前/尚未实现”指本文初次研究阶段；四份XML草案不是现行主题包格式，可导入包由本轮运行时回归导出。


日期：2026-10-30。本轮只读本机EVCC **3.3.3**，与既有 **2.9.46**静态文本比较，更新本项目设计及XML草案；没有修改运行代码、提升实际输出帧率、构建APK或操作车辆。新版APK与关键文件摘要、物理行号见[证据索引](../tools/evidence/evcc333-theme-pacing-20261030.json)。JADX混淆类名跨版本变化，下文不把类名变化当成功能升级。

## 1. 按用户最新要求调整方案

用户明确：先学习EVCC如何提高帧率和流畅度；帧率可设置，也可按内容动态调度，不锁死固定30fps；支持日夜配置和按组件覆盖样式。动态地图/动画以约30fps作为首轮验证场景，其他速率按用户设置、源帧率和目标实测能力验证，不能把静态页面反复发送30份相同图当作流畅度。

本项目采用以下设计方向：

- **XML → 结构化元素列表 → 同一组件绘制接口**，加载时编译；借鉴Simple Drive/Neon Stack的组合方法，自写组件与素材。
- **可设置帧率上限＋按需调度**：地图到帧、数据改变、动画、进度/歌词边界和过期deadline驱动；全部静止时只保留协议所需会话维持。
- **日夜模式和组件覆盖**：Day/Night/Auto、可共享两套配置，按组件ID覆盖；样式解析、资源与缓存按revision原子更新。
- 组件的Canvas绘制逻辑可共用。实投屏使用已有硬件Canvas Surface；Bitmap Canvas用于同引擎预览/导出和性能对照。是否让整帧软件Bitmap参与实时输出，须在1920×532实测，不能因EVCC使用Bitmap就推定它更低负载。

这些为本项目方案，下面第2–4节单列EVCC实际存在的实现。

## 3. EVCC到底是多少帧，怎样保持流畅

### 三条帧率链分别看

| 链路 | 源码事实 | 结论边界 |
| --- | --- | --- |
| Simple Drive / Neon Stack网络屏 | `qk6.lIl1:1678`读取`fpsLimit`默认10；`ch4.lI:94`限制1–30；默认画布320×820；`qh4:68`计算1000/fps毫秒 | 可配最高30fps，默认10fps；是上限，不是每种内容实际持续30fps |
| Dashcast投屏 | `ke0:2742`从dashcast_prefs取fps，默认30；`gh6:1786`导入配置默认30；`yo2:59`把传入fps设给MediaFormat frame-rate | 另一套投屏/编码配置；不能当作网络屏、组件动画或本车HAB已经实测30fps |
| Dashboard组件动画 | `DashboardGridLayout:252`初始33ms；`b61:4565`主页面设50ms；`co0:45`按轨道间隔限频，并在最后一帧强制提交终点 | 主页面组件回调名义上限约20fps；依附显示VSync，实际更新间隔还受刷新率和负载影响 |

以上引用的完整路径与准确方法锚点在证据索引。EVCC并非始终把帧率拉满。

### A. 帧开始到下一帧开始的节拍，而非工作完再睡整周期

`qh4.II:141`只在未有待执行任务、未停止、且有新快照或视频背景可复用快照时排任务：

```text
remaining = configuredPeriod - (now - lastRenderStartedAt)
remaining > 0：延迟remaining
否则：直接排下一次
```

`oh4.run:90`在绘制前记本帧起点，然后render→JPEG压缩→分包→send→重新检查。这样不会把绘制、编码、发送时间再额外叠加到一个完整帧周期上。若工作超过预算，也不代表能够实现配置fps。

### B. 最新快照与单个绘制待办

`ak:307`将最新非空快照写入`qh4.lI1`并唤醒worker；`qh4.l1I`限制实际绘制待办；`oh4:87`消费快照后清空，视频背景可继续复用上一快照。它避免按旧状态逐帧播放积压队列。

精确边界：快照到达仍会向Handler投递唤醒Runnable，不能据此声称整个Handler队列严格只有一个对象；受控的是实际绘制任务和最新状态。普通静态背景无新数据时不会只为填满fps上限而不断重画；视频背景是持续更新场景。

### C. 动画统一采样，替换旧轨道，结束即停

`u40.ll:192`先移除同组件旧轨道，再登记当前值、目标值、起点、时长、插值器、回调间隔和WeakReference；已有全局回调时不重复挂载。`co0.doFrame:26`计算随时间的插值、按间隔调用组件、确保终点提交，删除已完成/失去owner的轨道；无轨道就不再预约。`u40.onDetached:249`移除自身轨道。

这能改善数值变化的连续性，也避免每个组件一条循环。**所查路径未见根据CPU/GPU、温度或帧耗时自动升降fps的控制器**；统一动画调度与内容驱动刷新，可以成为我们“类动态帧”的基础，但自动策略属于本项目新增设计。

### D. 静态缓存、复用对象、按阶段测量

- `u40.Il:86`按画布尺寸/样式签名缓存静态Bitmap，稳定时直接绘制缓存；动态指针/数值另画。缓存失效才重建，不能据此说完全没有Bitmap分配。
- `bi4`在构造时分配画布、Paint、Matrix、RectF；每次遍历结构化元素，复用绘制对象。视频背景缩放/裁剪另有缓存，但JPEG压缩与分包仍有成本。
- `qh4.Il:162`每5秒记录实际发送fps及render、encode、chunk、send平均耗时、字节数、分包数、错误。它只统计该发送段，不能代表屏幕实际显示/手机到仪表延迟。
- 配置中的`chunkSleepMs`还会在UDP分包间等待；它属于网络传输负载的一部分，不能抄进我们的HAB共享内存通道。

### E. 可设置不等于当前会话可热调

`qk6.IIIl:641`保存网络屏参数；`qh4.I1`周期是构造时确定的final值；`NetworkScreenService:83`发现已运行会话会直接返回。所读设置保存路径未见给现有qh4更新周期的调用。因此不能把“有fps设置”描述为无缝动态热更新。我们若要求不重连HAB热调，应自己实现owner线程的revision更新。

## 4. 日夜配置与按组件覆盖，源码顺序

实际链为：

```text
.evccskin JSON → us5装载/保存 → rs5(day, night, shareDayNight)
 → ThemeManager选择当前模式 → 当前vs5中的全局token和widgetOverrides
 → u40按widgetId读取覆盖项 → 绘制/缓存失效
```

- `is4.llll:393`校验format=evccskin和schemaVersion≤1，`:317`读取shareDayNight、day和night；共享时两者引用同一模式配置。
- `rs5.ll:55`在共享或非夜间时取day，否则取night。
- `vs5`包含colors、chart、shapes、pageBackground、widgetOverrides；`us5.O0:99`按当前日夜模式和组件ID查覆盖项。
- `u40.O0/OO:123/134`对所查图表颜色的优先级是：**当前模式的组件覆盖值 → 当前模式全局chart token → 调用方提供的默认值**。属性未填才继承；不能把透明色0误当成“未填”。
- `us5.I1:23`保存/修改后通知本进程监听者及current_skin URI；Dashboard解除附着时移除皮肤监听。切换日夜要让静态缓存签名反映颜色/字体等变化。
- `lc6`有DEFAULT/DAY/NIGHT/AUTO。ThemeManager初始化读取Android uiMode，明确的DAY/NIGHT/AUTO分支可追；DEFAULT中有JADX不完整条件恢复，本轮不将该分支猜成确定算法，也不凭此推断本车灯光信号接入。

这里的皮肤用于Dashboard/View。Simple Drive/Neon Stack自己的网络屏元素仍在ci4中使用颜色与条件色对象；未见bi4自动读取us5/widgetOverrides。**两套能力可以由本项目统一，但不能声称EVCC已让所有网络屏元素自动继承Dashboard皮肤。**

## 5. 本项目怎样借鉴结构化内置组件

新增的两份自写XML组合草案：[Simple Drive启发](examples/cluster-theme-simple-drive-v1.xml)、[Neon Stack启发](examples/cluster-theme-neon-stack-v1.xml)。它们按L6画幅重新组合通用图元，未复制原盘面、字体或图片，也不称已完成可运行复刻。地图仍保留完整视频来源；布局只是组件设计示例，不作为最终原车安全显示区域定义。

| EVCC元素 | 本项目内置组件方向 | 比直接搬原实现补齐什么 |
| --- | --- | --- |
| Card / hc6 | CardNode：矩形/圆角卡片、背景、边框、透明度 | 支持样式token、组件覆盖和静态GPU缓存 |
| Text / jc6 | TextNode / ValueTextNode：静态文本、数据值、单位与对齐 | 标准字段、数据质量/新鲜度、缓存排版，未知显示-- |
| Bar / gc6 | BarNode：范围映射、方向、分段、阈值色 | 有效0与无数据分开；不复制样本缺失值处理 |
| Ring / ic6 | RingNode：圆弧、范围、颜色、起角/扫角 | 参数化绑定、范围/角度；不把源码中battery.soc硬编码为唯一输入 |
| Gauge / GaugeArc图表 | NeedleGaugeNode / ArcGaugeNode | 盘面缓存、转轴、真实目标追随、独立启动扫表 |
| 网络屏条件色 | TypedColorRule | 类型化阈值/状态规则，独立于布局；不让XML直接携带车辆写操作 |
| 组件动画轨道 | AnimationTrack | 全场景一套时钟，按组件/属性替换，seek/换歌/scene epoch取消 |

组件只接收`Canvas + 已解析props + 最新快照/视觉状态`；结构化元素由XML编译一次。相同draw代码可以向Bitmap Canvas和硬件Canvas绘制，缓存与资源寿命由对应后端拥有。Bitmap Canvas能够实现，但它是软件像素画布，不能把这一形式本身当作高帧率的原因。

## 6. 本项目帧率策略提案：上限、内容变化与测量分开

### 可设置的两种策略

| 策略 | 行为 |
| --- | --- |
| fixed-cap | 用户设置帧率上限；变化内容按此上限采样，静态仍不强行生成重复画面 |
| content-aware | 用户设置总上限与动画上限；地图新帧、车辆/媒体变化、活跃动画、下一时间边界共同决定下一次绘制/提交 |

配置中的30或60是草案示例，最终可用档位和默认值要随目标性能结果落实，不把60fps声明成已支持或已验收。地图源只有15fps时不能凭重复帧称有30fps真实地图；源地图30fps而指针动画可到60fps时，可以复用地图纹理只更新主题，但最终HAB能力仍须实证。

调度建议：

1. AutoCluster计算可见组件的下一deadline，统一绘制；AutoService合并最新地图/主题输入，并按用户上限提交。不能主题30、采集10而只在UI写“30fps”。
2. 使用单调时钟与截止时间，考虑工作耗时、VSync量化和33.333…ms周期；不把100ms改成33ms后继续沿用独立轮询/累计睡眠。
3. 热改设置时由owner原子应用policy revision并重算deadline，取消旧定时回调；保持Surface、地图解码器、HAB和QNX会话。实际消息队列也要有界，而非只有绘制标志有界。
4. 静态无变化时停止连续绘制；当前HAB仍需既有1秒会话维持。数据过期deadline不能被忽略，车辆全量采集范围与时效保持。
5. 管道/对端暂慢时继续保留最新待发帧，不积压旧帧；跨域槽位所有权/消费同步需与提高吞吐一起落实，不能用更快覆盖共享槽伪造流畅。
6. 发布requested cap、输入帧率、主题更新率、采集/发送/对端post率、帧龄、deadline miss和替换计数；p95/p99用于观察抖动。没有对端呈现时间证据时不将发送fps写成真实显示fps。

本项目已有的GPU Canvas、三缓冲最新帧邮箱、到帧唤醒及QNX去中转继续保留。当前100ms采集和主题100ms播放刷新仍在，约10fps限制尚未解除；下一批实现上述调度、设置与输出计量，再做相同场景CPU/GPU/PSS/线程/FD及延迟前后对照。尚未开始的原车告警根因与安全共存验收继续独立收口。

## 7. 本项目日夜/组件覆盖规则提案

- `appearance`选择day/night/auto以及shareDayNight。Auto先接Android明确的uiMode，已核验的车辆日夜来源随后通过统一契约接入；不猜属性ID，也不把“夜间皮肤”自动当成已改变手机地图配色。
- 样式按属性合并，建议从低到高：内置默认 → 组件预设 → 主题公共样式 → 当前模式全局样式 → 节点实例样式 → 当前模式该组件ID覆盖。这是我们完整合并规则；EVCC已经核到的是组件覆盖/全局token/调用默认这三层。
- 未设置继承；显式透明、0、false保留。布局/数据绑定/输出profile不由颜色皮肤覆盖项暗改。
- 日夜和样式改变只使相关缓存失效，在帧边界一次应用；同帧不能出现半日半夜的组件。资源/字体几何改变时重建必要排版，换色不重启车机服务。

XML中的render-policy、appearance、override及新增Card/Text/Bar/Ring都尚未进入运行解析器。它们是可评审、可校验的设计草案。

## 8. 复现与限制

`python3 scripts/verify_theme_proposal.py`验证本轮四份XML的引用/几何/策略/日夜覆盖格式，以及两轮静态源文件摘要和锚点；同时重算两个版本主题定义的637项字面量序列对照。它只做本机文档核验，不执行EVCC、不构建、不连接设备。

本轮没有实际帧率或功耗跑分。原始反编译中有推断类型、枚举和条件分支恢复错误；只从可追的方法与资源归纳机制，不将反编译文本当可编译SDK。动态负载自适应、HAB热调和统一网络屏样式是本项目新增设计，均未冒充EVCC现成功能。
