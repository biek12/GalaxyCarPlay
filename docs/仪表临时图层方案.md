# 仪表临时图层方案

日期：2026-10-30。回应用户“地图/音乐在顶层，能否放在其他图层上或下”的规划；本轮没有连接车辆、修改z-order或原车窗口。

## 1. 现状有三层含义

1. **Android合成内部**：`GalaxyHabComposition.kt:179`先建黑底，再加地图TextureView、导航卡和音乐View；它们先变成一张1920×532图像。QNX不能通过一个z值拆开这张图里的地图和音乐。
2. **QNX Screen窗口**：自有sender目标为display2/z4；原车现场记录为display2、1920×532、FULLSCREEN、order3。原始限定字段见`.local/research/hab-live-fixed-20261029/oem-before.txt`；这只描述该次被检查窗口，不能当作所有状态下的完整层级图。
3. **原车Kanzi场景内部**：背景、车速、告警可能属于同一个Screen窗口内的节点。外部窗口的z-order不能插入同一个Kanzi窗口的两个节点之间。必须先确认实际窗口/父子/组关系，不能从设计图推定有可插入的原车“地图层”。

现有输出是不透明的：`galaxy_hab_pixels.c:44`将第四字节写为255；`galaxy_hab_qnx.c:150`使用忽略alpha的`SCREEN_FORMAT_RGBX8888`。所以在Android把背景涂成透明，当前也不会在QNX露出原车车速。

## 2. 可调整什么

| 做法 | 技术状态 | 当前能否作为可见临时方案 |
| --- | --- | --- |
| 调整自己的QNX窗口z | `galaxy_hab_sender.c:115`已有签名ZORDER消息；`galaxy_hab_qnx.c:300`设置自己的`SCREEN_PROPERTY_ZORDER` | 接口已有，调整后的物理表现未实测；控制消息没有成功回执，必须读回并观察 |
| 把整张图置于原车窗口下 | 可以作为限定层级试验 | 原车若全屏不透明，地图和音乐会一起不可见；不能承诺“原车车速在上、地图背景在下” |
| 与原车设置相同z | 标准窗口排序仍受窗口管理与父子关系影响 | 不采用相同z碰运气作为产品排序规则 |
| 独立区域窗口置于已确认空闲区 | QNX支持窗口位置、尺寸和内容裁剪 | **建议临时主方案**；保留原车主要信息，地图/音乐只占已实测可用区域。需增加自有窗口的viewport配置，不修改原车窗口 |
| 透明合成、挖空原车信息区 | 标准Screen具备alpha/透明属性 | 当前输出链未支持，不能称“改一个z值即可”；需端到端保留alpha并在目标硬件验证 |
| 进入原车Kanzi节点之间 | 需要明确的原车场景集成接点 | 不属于本轮HAB外部窗口调序，不以它作为临时方案前提 |

QNX文档明确z-order相对于父窗口，应用窗口还受窗口管理规则影响；position与size是独立的布局属性。透明的实际效果取决于硬件合成能力。[QNX 7.0属性文档](https://qnx.com/developers/docs/7.0.0/com.qnx.doc.screen/topic/screen_8h_1Screen_Property_Types.html)

## 3. 临时方案的实施顺序

1. 下次授权联网后只读枚举display2的窗口、父子/组、可见性、position、size、z和像素/透明属性；覆盖当前原车页面及提示状态，建立实车可用区域图。
2. 用现有ZORDER控制只调整自有窗口，验证“原车之下”和“原车之上”的实际关系；每次都能STOP释放恢复原车。目标z根据枚举结果决定，不把2/4写成跨状态通用规则。
3. 在 **AutoService投屏会话** 中实现`viewport{x,y,width,height}`和相对摆放策略，优先让独立窗口占用已确认区域。临时版不画假车速、不把原车速度和告警擦掉。
4. 如需不规则区域共存，再做明确版本的alpha合同：Android生产者/像素转换→共享区格式→QNX带alpha的像素格式→透明模式→硬件结果逐层验证。不能悄悄改变现有v1的不透明格式语义。
5. 完整主题由独立仪表App制作，经AutoService融合后输出。临时窗口共存不是取消完整仪表需求，而是当前已有内容可用、车辆数据迁入前的阶段形态。

设计参考中的车速位置不是原厂界面的保护区域坐标；具体viewport由本车真实窗口和显示内容落实。本轮只规划，不对离线车辆执行层级试探。
