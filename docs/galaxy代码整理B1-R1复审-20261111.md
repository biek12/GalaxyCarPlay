## F1 [P1] cluster 指令给遮罩额外留下了独立地图意图

源码证据：

- R1候选 `AutoService.kt:618-625`：`cluster` 先 `requestLegacy("command")`，又启动 `ClusterRenderService`；该命令本身会启动所选 Cluster 模式，不等于一次独立 map-only 选择。
- R1候选 `ProjectionOwnership.kt:128-130`：THEME 退出只清 `themeRequested`，不清遗留的 `legacyRequested`；`:143-153` 因而转为旧地图输出。
- 实际产品 `ClusterRenderService.kt:53-55,71`：遮罩通过THEME运行，`onDestroy`关闭输出；`AutoClient.kt:330-350`最终detach。服务端detach会重新决策。

实跑：`requestLegacy("command") → THEME=true → THEME=false`（MAP持续在线），结果从 `explicit:theme` 转成 **`active=true reason=explicit:legacy:command legacyIntent=true`**。这既会在退出后接上地图，又会把错误地图意图保存在新键中。

要求：区分启动所选Cluster模式的命令与独立map-only请求，按实际入口及所有者撤销，不让一次遮罩启动留下另一项独立工作。保留真正用户map-only请求的恢复，不能靠一律删除持久化或强关能力掩盖。

## F2 [P1] 服务重建后的空控制器被误当作旧 Hook 已释放

源码证据：

- R1候选 `ProjectionOwnership.kt:164-165`：`elementsState == null`直接放行。
- R1候选 `AutoService.kt:716,917-925`：输入来自当前服务内的 `clusterHook`，而控制器只在当代 `elementsWanted` 时创建。服务对象重建没有控制器，不代表QNX没有旧所有者。
- 产品 `KanziMediaPublisher.kt:53-55`：租约有效期是发布时间后5000ms；`tools/research/g733_hook_runtime.sh:59-67`的独立guard通过连续失去健康状态触发恢复。Android服务消失与QNX Hook退出不是同一时刻。

实跑反例：旧增强在运行 → 用户提出旧地图请求（被保留为pending）→ 新建状态对象并恢复该工作意图 → MAP先重连、元素控制器未创建。结果 **`active=true reason=explicit:legacy:restored`**；此时没有旧Hook释放证据。

要求：重建后区分“已证明没有旧所有者”和“本代尚未核验旧所有者”。启动门槛须有所有者/代次及实际运行证据，不能把内存null/初始idle当跨进程证明。原guard的到期机制不等于允许用固定等待伪造恢复。保持正常无增强历史的启动路径可用，不引入无依据永久禁用。

## F3 [P1，仍未完成] HAB→元素的释放回执不能只靠 Kotlin 进程退出

R1如实列为未完成，接受其事实表述，不接受“启动侧已经整体闭合”的泛化结论。

核对到的现有链路：

- `GalaxyHabComposition.kt:80-101,285-305`：`connectionChanged(false)`在worker释放前通知；close后异步清理。
- `GalaxyHabProcess.kt:65-71`：`abortAndWait`证明本地子进程退出，可能包含强制结束。
- `galaxy/service/src/main/cpp/hab/galaxy_hab_sender.c:17-29`明确写着“STOP不等ACK”。
- `galaxy_hab_qnx.c:360-366`在收到STOP后才调用QNX平台close，未向发送方返回关闭完成证明。

所以只新增一个包装 `child.waitFor()` 的 `released` 回调，仍不足以证明QNX窗口/导入资源已释放。必须区分发送端退出、接收端会话关闭、窗口/消费者释放；异常退出没有完成证据时不能标成功。
