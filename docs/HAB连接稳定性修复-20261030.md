# HAB连接稳定性修复（待复车）

## 指定固件现场结论

用户于2026-10-30确认已收到完整地图和音乐画面，并指出触发概率低；当前布局仅做快照，后续重做，见[布局记录](仪表布局快照-20261030.md)。本轮没有改布局。

已确认一个造成“握手后立即断开”的接收端生命周期缺陷：

1. 旧接收进程等待在`habmm_socket_open`，收到TERM时信号处理只置`probe_stopping=1`；现场该阻塞没有立即返回。
2. 此时另启接收进程，旧等待仍可能先取得下一次连接。旧实现的`galaxy_hab_qnx_open`没有检查停止请求，继续准备隐藏窗口并发送成功ACK。
3. 回到`qnx_probe.c`后，`while (!result && !probe_stopping...)`直接跳过帧循环，关闭VC。对应旧QNX日志明确为`RECEIVER_READY_ACK=0`、`RECEIVER_LOOP_RESULT=0`、`RECEIVER_CLOSE=0`。在serve模式下，这种result0退出只能由停止标志触发；不是收到正常STOP（其返回1）。
4. Android00:24:00.919记录ready，00:24:01.054即`result=-19 cleanup=-19`，与对端刚ACK就关闭相符。另一种00:30:37的`-4`是发送进程12秒等待期限触发，不能把它与`-19`混为同一阶段。

另一个确定的易复发问题：旧serve每次STOP/断开后整个进程退出，下一次连接前需要手动启动；Android一旦pipe失败，当前会话也没有恢复，必须再重启App。这两端一次性生命周期共同造成对启动时机的依赖。

开启逐步返回码后，原APK在00:31:19.666再次握手成功，之后已观察到100、200、300帧持续提交；QNX逐步日志显示`screen_post_window RETURN=0`。用户随后确认实际可见。独立应用UID的一帧/STOP测试也得到双方正常close0。这证明内容/权限/显示通路能工作，但不代表新稳定性修复已复车。

## 本次修复

- `galaxy_hab_qnx.h`提供owner停止查询；`galaxy_hab_qnx.c`在阻塞open返回、AUTH接收后、准备窗口后/ACK之前重新核对。已取消的等待返回`-EINTR`并释放自身资源，不再先ACK再退出。
- 自有候选入口的serve模式在同一进程内接受下一会话；每代完整关闭窗口、PMEM和VC后才重新监听。没有并行owner，不靠循环写窗口抢占原车。认证/协议错误立即退出；连续三次空会话/建链错误停止恢复。
- 增加会话编号、处理事件数、停止标志、帧校验和各平台调用结果，区分TERM、正常STOP、断线与显示错误；不输出密钥、地址或像素。
- Android `GalaxyHabReconnect`在同一CarPlay会话内以1秒、3秒延迟提供最多两次恢复；迟到回调仍受会话代次约束。单纯ready不清空预算，持续提交100帧后才允许新一轮有限恢复。没有无限重连或改为其他输出路线。
