## R1 [P1] 新遮罩请求在旧元素租约尚未退出时被永久清除

证据：

- 候选 `ProjectionOwnership.kt:103-115`：THEME 上升沿调用 `markExplicit("theme")`，但同次输入只要 ELEMENTS 仍为 true，立刻清除 `explicit`；之后 ELEMENTS 下降沿不会恢复这次新请求，THEME 也不再有上升沿。
- 产品 `galaxy/cluster/src/main/java/com/galaxy/autocluster/ClusterRenderService.kt:53-55`：先调用 `elements.close()`，随后立即创建并启用 THEME。
- 产品 `galaxy/client/src/main/java/com/galaxy/auto/client/AutoClient.kt:27-28,330-350`：每个客户端有独立 worker；`close()` 的服务端 detach 排到旧 worker，第350行并不等待完成。THEME 的新连接/激活通过另一 worker 发出，不能依据客户端代码行顺序假定服务端 ELEMENTS 已被移除。

直接执行冻结类的反例输入：

```text
MAP=true / THEME=false / ELEMENTS=true
MAP=true / THEME=true  / ELEMENTS=true   # 新的显式遮罩请求先抵达
MAP=true / THEME=true  / ELEMENTS=false  # 旧元素 detach 后抵达
再次评估相同最终输入
```

实际最后两次均为 `active=false reason=data_source_only`，新遮罩不能启动。此问题不同于禁止旧地图复活：这是丢弃了新的合法启动意图。

修订要求：保留新请求的所有者/时序身份，使旧模式的延迟撤销不能抹掉新模式请求。沿已存在的客户端/服务接入落实，不把租约上升沿一律当作用户动作，也不在两个 App 各维护一套互相推断的布尔条件。禁止用固定延时、无限重试、重复开关规避。最小回归直接运行修改后的生产职责，覆盖这两个服务端事件顺序，并明确实际入口是否验证。

## R3 [P1 / 既有缺口未闭合] 租约消失仍被当作原生显示资源已释放

证据：

- 候选 `AutoService.kt:671-691`：只把当前角色 active 传给决策器；一旦得到 true，立即创建合成器并启用 HAB，没有输入原生恢复/关闭完成状态。
- 产品 `ClusterHookController.kt:43,64-73,96-103`：停止是独立 worker 的 op11 请求，最长等待40000ms，收到并验证 `state=restored` 后才在主线程报告。ELEMENTS detach 不等于此过程已经完成。
- 交付 `CHANNEL_AUDIT.md` §4.2把“先 close 客户端，再取得另一租约”叙述为资源交接顺序；该证据不足以证明原生旧所有者已释放。任务书 §5.3要求旧输出停止/释放后新所有者才提交。

因此，即使最终状态意图正确，切换瞬间仍可能在原厂 Hook 恢复期间启动新的 HAB 输出。这里是源码可达路径及本批未满足的交接要求，未声称已经观察到设备同时出画面。

修订要求：以已有真实完成回执作为交接门槛，分清“想停止”“正在恢复”“已释放”“新输出待启动”；失败保持真实阶段，取消/新代次须使旧结果失效。两方向的交接都列出实际资源完成点，不能用租约 false、Root ready、文件存在或固定等待替代。涉及当前白名单外文件时，先交精确接口请求；先完成可独立修订部分，不自行扩大接入探索或执行设备命令。
