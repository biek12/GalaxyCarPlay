## 2. 已确认缺陷与源码位置

### A [P1] 正常停止路径撤销了自己的释放任务与回调

R2 `AutoService.kt:1384-1398`先设 `habReleaseConfirmed=false`、调用 `setSessionActive(false)`，同次调用又立即 `composition.close()` 并丢引用。

R2 `GalaxyHabComposition.kt:110-131`先 `bridge.close()`，再排 `finishAndAwaitRelease()`；`:406-423`的close设置closed、删除全部worker任务，另排abort，不做释放完成通知。若先前任务已在执行，回调还被 `if (!closed)` 丢弃。PREVIEW未保留时这是正常必经路径，不是极端场景。

所以新增CLOSED协议并不等于服务已经能收到完成信号；当前切换可永久卡在未确认。

### B [P1] 平台清理失败仍发成功CLOSED

R2 `galaxy_hab_qnx.c:158-165`不检查 `release_display()` 返回值即编码发送CLOSED。`release_display():102-113`还在销毁/unmap/unimport失败后清掉句柄字段。

用其原有失败fixture直接驱动候选：`result=-5`（`-EIO`），但 `closed_receipts=1`。这证明错误清理结果仍被发布为成功证据；不声称host已经证明真实QNX资源泄漏。

### C [P1] 重复close把未确认洗成已释放

R2 `galaxy_hab_sender.c:30-47`第一次close清ready，校验错误回执后released为0；第二次落入 `!ready` 分支，无条件改为1。

实跑其同会话不匹配fixture后再close一次：`released=1 expected=0`。此外，“从未ready”也可能是INIT已发送但ACK未收到，不能一概当作对端没有窗口。

### D [P1] 重建核验依赖的是用户开关，关闭窗口内仍丢证据

R2 `AutoService.elementRouteEngaged():1449-1450`只读 `clusterElementsEnabled`；`setActive():398`、THEME接管`:385`及theme-stop`:1147`会在原生恢复完成前清该键。若在清键后、`restored`前进程退出，新服务仍会把空控制器判为NONE。它不是独立、持久的“原生所有者尚未释放”证据。

### E [P1] 元素接管不再作废旧遮罩意图

R2 `ProjectionOwnership.applyLeaseEdges():143-145`在ELEMENTS上升沿只调用 `supersedeLegacy()`，保留旧themeRequested。实跑 `THEME=true → THEME=true/ELEMENTS=true → THEME=true/ELEMENTS=false`，最后为 `active=true explicit:theme`。旧遮罩被动恢复。

### F [P1 / 兼容链未完成] 新能力没有在握手时区分，旧接收端可先被接入后永久阻塞切换

R2新增CLOSED却仍使用owned version=2；旧v2握手成功后会绕过既有接收端准备。等停止才发现没有CLOSED，不能再以“需要同批部署”代替App已授权的按需检查/升级流程。

## 3. 确定修复方案：按以下顺序实施

### S0 编译与import先修

落实G的两条import。所有6份候选内的代码类型引用全部先import，尤其 `GalaxyHabComposition.open()`中的 `RootHabProcess`及 `setMapStreamSize()` 的 `MapStreamSize`；换行拆开的完整类名仍不合规。保留字符串/Manifest中的协议类名。

### S1 一个退出事务，直到完成后才销毁对象

修改 `GalaxyHabComposition.kt`、`GalaxyHabProcess.kt`、`AutoService.kt`；不要新建通用Manager。

固定状态：`NEVER_STARTED / ACTIVE / RELEASING / RELEASED / UNCONFIRMED`。固定回执身份：

```kotlin
data class HabReleaseToken(val owner: String, val epoch: Int)
data class HabReleaseResult(
    val token: HabReleaseToken,
    val confirmed: Boolean,
    val reason: String,
)
```

这两类只表示本链路退出事务，可放projection包单独小文件；owner为每个Composition创建时分配的UUID，epoch为退出的那一代会话。不能用当前最新epoch给旧结果重新贴标签。

`GalaxyHabComposition`固定实现规则：

1. `setSessionActive(false)`进入私有 `beginRelease(disposeAfterRelease=false)`。先把active置false、停止绘制和frameWake，作废后续connect/pump调度；**不调用 `bridge.close()`，不删除释放任务**。
2. 在唯一worker中按顺序等正在执行的本代写帧结束，再对捕获的旧process执行一次 `finishAndAwaitRelease()`。正常退出先写STOP、flush、关stdin、等真实CLOSED；超时/异常才强制回收本地进程，并返回未确认。握手取消与写帧watchdog异常同样只能产生未确认，不能冒充已释放。
3. `close()`不另走abort分支。它置 `disposeAfterRelease=true`并复用同一 `beginRelease`；若退出已在执行，不再重复提交、不移除现有worker任务。
4. 本代释放结果生成后只投递一次 `HabReleaseResult`，**即使Composition已经禁止继续工作，也必须投递该终态结果**。回调不能被 `if (!closed)`吞掉。
5. 终态结果生成后才清bridge、回收graphics/reader/frames并退出对应线程；继续预览的场景仅退出输出会话，不销毁预览资源。不能因保留PREVIEW而允许另一原生输出提前启动。
6. `connected()`仅报告ACTIVE，删除 `releaseChanged(true)`；成功握手不是本会话已释放。未知的旧回调不得改新一代会话状态。

`GalaxyHabProcess.finishAndAwaitRelease()`固定顺序：

```text
worker停止继续写帧 → STOP写入/flush → stdin关闭
→ 等本child的真实CLOSED/EOF/截止时间
→ 记录confirmed（只有正确CLOSED为true）
→ 确认本child退出，必要时强制回收
→ 返回真实结果；退出/超时不能把false改成true
```

`AutoService`固定接线：

- 用 `retiringComposition`和 `pendingHabRelease: HabReleaseToken?`保留正在退出的对象/身份；不能在请求停止后同次立即丢掉最后引用。
- 启动退出前先登记pending token及RELEASING，再调用旧对象停止，避免同步完成回调先于登记。
- 停止回调仅当token等于当前pending token时有效；旧对象/旧代次回执直接忽略。匹配confirmed=true才清pending、开放元素启动，然后重算并发布。
- 匹配confirmed=false时本地资源仍可收尾，但门槛保持UNCONFIRMED；保留失败原因及原生所有者记录。重复apply只重新请求真实核验，不创建并发输出、无限循环或假成功。
- 用同一协调入口同时计算“旧HAB是否运行”和“元素是否获准启动”。`publish()`可以发布状态，不能凭快照调用顺序越过该入口。无需在本批拆整个publish/binder。

### S2 关闭证据必须可信且幂等

修改 `galaxy_hab_qnx.c/.h`、`galaxy_hab_sender.c/.h`、bridge及对应host测试。

QNX固定规则：

1. `galaxy_hab_qnx_stop()`先保存会话身份，再执行release_display；**只有返回0且没有历史清理失败标记时才发送成功CLOSED**。失败仍努力清理/关闭通道并返回原错误，但不发成功CLOSED。
2. 每个资源字段只在对应释放成功后按实际所有权更新；不能无条件把失败句柄清零用来证明资源已释放。保存本次清理失败状态，重复close不能把上次失败洗成成功。
3. 窗口/消费者、context、scratch、mapping、import全部处理完成后才能发送；通道关闭和pmem收尾按既有职责执行。新握手/新会话才允许重置该会话失败记录。

Sender固定规则：

1. 增加最小 `close_started / close_result / peer_may_own`字段。`peer_may_own`在尝试发送INIT之前置true；send返回错误也不能认为对端一定没收到。
2. 首次close缓存结果；重复close直接返回缓存结果并保持released原值，不再次发STOP/读回执、不因ready=false修改证据。
3. released只能来自正确同会话CLOSED，或可证明从未将INIT暴露给接收端。INIT已尝试、握手未完成、超时、错误会话及回读失败全部保持0。
4. 新的一次有效open（通过未在使用检查后）或显式init才重置上述会话字段；不把上代失败传成下一代成功。
5. bridge输出真实结果；Kotlin只消费本child的严格0/1结果。不得用子进程退出码0或`ready=false`代验对端释放。

### S3 原生未释放记录与产品开关分开保存

修改 `AutoService.kt`和 `ClusterHookController.kt`。内部字段已经由Lead批准，不需再提交用户逐键确认。

新增最小持久记录：`platform/elementReleasePending`及对应 `elementOwnerToken`；HAB同理保存 `habReleasePending`及token。它们表示“本应用原生所有者可能仍存在”，不表示用户选择的模式或新UI开关。

固定写入/清除点：

- **在任何原生ensure/输出可能创建所有者之前**，由专用SerialWorker提交pending+token，提交成功回主线程且请求代次仍匹配后才允许副作用。磁盘操作不能放UI/Binder线程；不要求每帧写盘。
- 用户关闭、THEME接管、Binder detach、theme-stop或配置草稿变更，都只撤销工作意图，**不能清pending记录**。
- 只有本owner/token对应的真实 `restored`或CLOSED（以及明确的自有所有者已不存在核验）才清pending。先确认结果、再持久化清除、再放行新所有者，保持代次检查。
- `onCreate`先读记录再处理客户端：pending=true一律UNVERIFIED，即使 `clusterElementsEnabled=false`。现有控制器 `verifyReleased()`通过已核验的op11 stop取得restored；不能把新控制器idle当作释放。
- 首次升级而没有新记录时，不把“缺键”当作无旧所有者证明；旧安装进入一次真实所有者核验。正常全新安装的NONE必须对应初始化前从未创建过自有原生所有者这一事实。不得为消除等待伪造NONE，不改变用户Root/automatic关闭选择。
- 关闭后崩溃、pending清除写盘失败、Root暂不可用时保持真实未确认状态并按现有有限恢复机制处理；不要定时等待后直接认为释放。

### S4 修复旧遮罩复活，同时保留新请求

`ProjectionOwnership.applyLeaseEdges()`按如下次序明确处理：

```kotlin
// 元素上升沿先作废接管前的两种旧意图。
if (elementsActive && !elementsLease) {
    supersedeLegacy()
    themeRequested = false
}
elementsLease = elementsActive

// 再处理本轮新THEME边沿。ELEMENTS在场期间的新THEME请求因此能保留。
if (themeActive != themeLease) {
    themeLease = themeActive
    if (themeActive) supersedeLegacy()
    themeRequested = themeActive
}
```

保留R2中 `cluster`不产生独立legacy请求的修正。不能在elementsActive每一轮清themeRequested，否则会重新引入B1的原反例。

### S5 接收端能力在开始显示前协商，不留给用户手动装新接收端

固定采用现有自有owned协议的 **version=3**（64B布局和现有magic不变），含义为v2的每帧一致性要求加“关闭完成回执为必需能力”。改 `galaxy_hab_owned.h`版本及必要注释，不另猜厂商协议。

执行链固定如下：

```text
现有App/HAB尝试 → v3 HELLO/READY验证
  → 成功：沿同一会话输出
  → 老v2不支持：完整清理本次尝试并保留未确认资源证据
    → 经既有prepareReceiver / QnxReceiverLifecycle / QnxReceiverRemote
    → 核对自有程序路径、owner key和当前APK资产摘要
    → 停止并确认自有旧接收端退出，部署本批v3接收端
    → v3重新握手成功，才允许输出
```

遵守普通身份HAB优先与用户Root关闭选择。不能降回v2仍称支持CLOSED，不能无限重试。已有自动准备链失败时报告具体阶段；不得把正常流程改成人工安装或额外登录QNX。
