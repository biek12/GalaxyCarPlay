> 后续实施更新（2026-10-30）：本文保留前一研究/优化阶段的原始证据。当前已实现可视化编辑器、24类/72预设、日夜/组件覆盖、EGL合成、可配置按内容刷新及自有GLC2消费确认；删除原100ms采集/主题轮询上限。当前源码与准确入口见[实施方案](Cluster可视化主题编辑器实施方案-20261030.md)，验证见[上车验收](Cluster上车验收-20261030.md)。实际显示帧率、8155负载与原车告警仍未实车验收。下文“当前/尚未实现”指本文初次研究阶段；四份XML草案不是现行主题包格式，可导入包由本轮运行时回归导出。


日期：2026-10-30。目标仍为银河L6 2023 Max / FlymeAuto 2.3.1。本轮完成第一批本机代码整改与验证准备；没有连接、安装或操作车辆。

## 结论与证据等级

- **用户反馈**：地图/音乐已经可见，投屏期间出现“仪表图传异常，请联系服务站”。提示原文按用户描述记录，尚无本次发生时的QNX故障码、监测状态和窗口快照。
- **源码存在**：修改前主题使用软件Surface Canvas；地图是CarPlay 111经MediaCodec输出Surface，并非Canvas重新绘制地图。帧合成后有多次CPU搬运，输出被100ms采集节拍限制。目标保留硬解路径，实际选中的decoder仍需实车回读。
- **本地原厂材料存在**：QNX HMI/Middleware有黑屏、动画、自检、告警区状态上报链；原车车速、挡位也出现在QNX数据源定义中。不能按“固定图标来自QNX，其他全部来自Android”划分安全边界。
- **本轮已改**：主题使用硬件Canvas；新帧到达唤醒发送；QNX删除整帧中转；保留私有slot快照和校验；补Android阶段计时和全部QNX窗口的三阶段快照。
- **未证明**：8155实际CPU/GPU负载降低比例、端到端延迟、监测链具体触发条件、告警消失、原车安全显示不受影响。编译或本机合成帧对照均不能代替这些实车结果。

## 当前帧链及成本

```text
CarPlay MediaCodec → 地图Surface / TextureView ─┐
AutoCluster主题Surface → TextureView ──────────┤
                  私有VirtualDisplay合成 → ImageReader
                  → Java三缓冲最新帧邮箱 → pipe
                  → native RGBA转BGRA → HAB共享ring
                  → QNX PMEM导入 → 私有scratch校验 → Screen可写buffer → post
```

关键接点：

| 环节 | 当前文件/方法 | 判断 |
| --- | --- | --- |
| 主题绘制 | [ClusterRenderService:35](../galaxy/cluster/src/main/java/com/galaxy/autocluster/ClusterRenderService.kt#L35)，旧ClusterRenderer（已由SceneRenderer替换） | 已改`lockHardwareCanvas()`；每次CLEAR并完整重画透明主题，满足硬件Canvas不保留buffer内容的要求 |
| 合成/采集 | [GalaxyHabComposition:70](../galaxy/service/src/main/java/com/ecarx/autoservice/projection/GalaxyHabComposition.kt#L70)、[captureFrame:202](../galaxy/service/src/main/java/com/ecarx/autoservice/projection/GalaxyHabComposition.kt#L202) | 私有VirtualDisplay、两个TextureView、RGBA ImageReader；仍有GPU到CPU可读图像及逐行复制 |
| 发送节拍 | [GalaxyHabLayout:11](../galaxy/service/src/main/java/com/ecarx/autoservice/projection/GalaxyHabLayout.kt#L11)，[pump:177](../galaxy/service/src/main/java/com/ecarx/autoservice/projection/GalaxyHabComposition.kt#L177) | 100ms采集上限仍在；原先还每100ms轮询发送，现改新帧到达唤醒，静态时1秒维持会话。没有把现有采集上限提高成30fps |
| 本地进程 | [GalaxyHabProcess:63](../galaxy/service/src/main/java/com/ecarx/autoservice/projection/GalaxyHabProcess.kt#L63)，[bridge:13](../galaxy/service/src/main/cpp/hab/galaxy_hab_bridge.c#L13) | Java数组经过pipe送隔离sender；隔离驱动阻塞有价值，像素走pipe仍有搬运成本 |
| 像素转换 | [pixels:7](../galaxy/service/src/main/cpp/hab/galaxy_hab_pixels.c#L7)，[sender:91](../galaxy/service/src/main/cpp/hab/galaxy_hab_sender.c#L91) | RGBA→BGRA并填充alpha255；不是GPU buffer直接跨域展示 |
| QNX接收 | [receiver:151](../galaxy/service/src/main/cpp/hab/galaxy_hab_receiver.c#L151)，[qnx:261](../galaxy/service/src/main/cpp/hab/galaxy_hab_qnx.c#L261) | 原来mapping→scratch→pixels→Screen；现在mapping→scratch→Screen，校验通过才写Screen |

1920×532×4 = **4,085,760字节，约3.90MiB/帧**。一次整帧搬运在10fps时传递40.86MB/s有效数据，单计读写约81.72MB/s；30fps对应122.57MB/s有效数据、约245.15MB/s读写。这只是**一次复制**的算术量，不是实测DRAM流量或整机带宽占用。

保留Canvas API并不妨碍GPU绘制。Android明确`lockHardwareCanvas`返回硬件加速画布，且要求每次完整覆盖Surface；硬件View也支持常用Canvas操作。[Surface API](https://developer.android.com/reference/android/view/Surface#lockHardwareCanvas())、[硬件加速绘制](https://developer.android.com/develop/ui/views/graphics/hardware-accel)。本轮没有把“GPU渲染”写成“零CPU/零复制”。现有[MediaCodec配置:1395](../shared/src/main/java/com/shilapi/xcertplay/media/AndroidMediaSink.kt#L1395)把解码器配置到Surface；本轮未修改该解码链，也未实测decoder硬件身份。

## 本轮实现

1. **主题改GPU Canvas**。继续保留透明主题、文字、封面、进度、歌词、车辆读数与三个面板；用`Trace`标记绘制段。连续绘制故障仅记录一次错误类型，避免静默失败或刷日志。封面替换后交由Bitmap/RenderThread引用生命周期释放，避免GPU仍引用旧图时主动`recycle()`。
2. **QNX去一份中转**。新增`galaxy_hab_receiver_frame_strided()`，直接将已校验scratch写进Screen的实际stride；删除`q->pixels`分配及逐帧中转。少4,085,760字节自有缓冲及一次有效整帧复制。继续校验目标容量、stride、格式、别名、完整slot和采样hash；坏包/坏hash不污染待显示buffer或输出info。
3. **保留跨域快照**。共享ring仍由sender独立轮转；当前无逐帧消费ACK/fence。不能把共享slot指针直接交给Screen持续扫描，也不能删掉scratch冒称零拷贝。提高帧率会缩短6槽的复用周期，需要先落实消费所有权与超时处理。
4. **补测量出口**。AutoService dumpsys增加`copyMicrosMean/Max`、`pipeMicrosMean/Max`、`acquireToPipeMicrosMax`，时间戳跟随真正保留的邮箱帧。这些值只覆盖取得Image到本地pipe写完，**不代表QNX显示完成**。只读性能脚本加入CarPlay和SurfaceFlinger；SurfaceFlinger单列，不计作自有进程CPU总量。
5. **告警取证准备**。`tools/hab/snapshot-qnx.sh before|during|after`读取所有Screen context窗口的限定显示属性，避免只看`cluster-hmi`遗漏独立告警层。原车窗口仅只读，三个阶段分别保存。
6. **到帧唤醒**。[GalaxyHabFrameWake](../galaxy/service/src/main/java/com/ecarx/autoservice/projection/GalaxyHabFrameWake.kt#L7)在采集到新帧时提前替换心跳等待；慢write期间仅保留一个待办，邮箱继续替换旧帧。停止/重启替换Runnable身份，旧代已出队回调无效；发送仍由单worker持有，不增线程。该修改消除原来的独立100ms轮询等待，实际节省延迟仍待车上计时。

以上不改变HAB认证报文/帧格式、QNX显示ID/层级、车辆采集范围和时效；退出仍只隐藏/销毁自有窗口并释放自有import/VC。

## 适合后续实时输出的方案

建议路线是**地图保持硬解Surface，主题保留GPU Canvas，AutoService用EGL/GLES统一合成，native持有有界帧缓冲和消费同步**。不为文字、歌词全部重写一套Vulkan绘制器。

| 路线 | 可以解决什么 | 必须落实的条件 |
| --- | --- | --- |
| 硬件Canvas主题（本轮已做） | CPU逐像素绘制主题的开销 | GPU负载与Surface生命周期仍须实测；并未消除输出读回 |
| EGL/GLES采样地图和主题SurfaceTexture（下一阶段建议） | 去掉私有Presentation/VirtualDisplay/TextureView的中间装配，集中决定何时合成 | 单EGL owner线程、输入变换矩阵、GPU fence、Surface失效/代次处理；保留完整111画面和主题内容 |
| native直接取得输出并交给sender（下一阶段建议） | 避免Java整帧数组和像素pipe搬运 | 正常App/UID0两身份都要有明确FD/内存所有权与取消释放；不能让新路径破坏已优化的普通身份直连 |
| HAB可导出的GPU/原生buffer（需目标ABI核验） | 进一步减少读回/格式转换/跨域复制 | AHardwareBuffer/gralloc与HAB export、QNX PMEM/Screen的互操作、像素格式、cache一致性、producer/consumer fence逐段实证；普通Android buffer并不自动等于QNX可扫描buffer |

Android的SurfaceTexture允许GPU直接采样BufferQueue，要求所属EGL context在调用线程current；还必须使用输入变换矩阵。[SurfaceTexture架构](https://source.android.com/docs/core/graphics/arch-st)。这为GPU合成提供依据，不证明本车HAB已支持直接导出该纹理。

本轮已先实现采集到帧后唤醒发送。后续合成节拍也应由输入到帧事件触发，合并同一刷新周期更新；地图按实际源帧到达，主题按可见数据/进度/歌词变化更新，静态内容复用。目标先以30fps动态输出验证，再按源帧率和实测预算推进；这是性能目标，当前仍约10fps上限，不能写成已达到30/60fps。邮箱只留最新待发帧，旧运动帧不排队播放。地图输出时效与全量车辆采集分开，不能为降负载删采集字段或降低原有时效。

## 原车图传与提示

本轮**没有获得可安全停用的原车Android→QNX独立内容通道清单**，因此不执行掐断、kill/STOP原车进程、修改Screen配置或绕过告警。正常释放自有窗口仍按既有方案执行。原车流程与自有HAB会话不是可互换的健康证明。

可核验的原厂证据集中在[静态证据摘要](../tools/evidence/projection-render-research-20261030.json)，含原文件SHA256、准确文本行号或ELF文件偏移；偏移不是运行时地址：

- `ClusterDataSource.xml:27`、`:30`、`:55`分别定义Speed、SpeedValid、GearType；`:20`定义UnresolvedWarnId。说明至少这些原车内容在QNX数据模型存在，不证明固定位置图标全由哪一处理器独占绘制。
- `cluster-hmi` ELF文件偏移`0x2a263`有`SafetyAppsProxy::sendBlackScreenSts`符号，`0x2a340`有`sendKanziAnimationSts`，`0x7bd768`有黑屏/动画状态上报静态日志串。
- `libMiddleware.so`有`SafetyAppsTimer_1S`、`sendSelfCheckSts`、`sendCAreaTelltale`、`sendAAreaWarningId`；`libMidProxy.so`存在对应`safetyapps.sih`消息类型。它们证明上报接口存在，**尚未证明昨天告警的判定方法、超时阈值或CRC检查区域**。
- 已采集`graphics.conf`声明C2D blit、Adreno gralloc、display1/2为1920×532@60；它不是运行时所有窗口的硬件pipeline分配表，不能把该配置的层号照填为我们可以占用的层。
- `apps/cluster/common/bin/startup:159`启动原车cluster-app，`:200`启动cluster-hmi并纳入monitor；本轮只读，不改原车启动/监控。

**推断待证**：提示可能关联原车内容源/心跳失联、合成/图层资源争用、原车显示内容完整性监测，或其他原车故障状态。新增不透明置顶窗口也可能改变合成策略或覆盖监测区域。现在没有证据在这些原因之间定案，更不能归结为“Canvas慢”。

QNX会按可见窗口、像素格式和硬件pipeline能力选择合成方式，覆盖底层画面并不自动让原生产者停工；强行占指定硬件pipeline也可能改变整机场景。[QNX 7.1合成机制](https://qnx.com/developers/docs/7.1/com.qnx.doc.screen/topic/manual/cscreen_composition.html)。原车停止发送会否触发本次提示、会否丢失车速/告警等内容，必须沿本车具体通道判断；目前不能保证安全，也不能保证节省多少负载。

**复车诊断顺序**，均保持原车服务正常运行：

1. 原车正常状态、自有会话未启动，记录窗口/原车故障状态与CPU基线。
2. 自有AUTH/INIT/ACK完成、窗口仍隐藏，区分“建会话即异常”和“显示后异常”。这是诊断程序场景，不是默认App新增手工按钮。
3. 自有固定静态帧，再到完整地图+音乐；对齐告警首次出现时刻、HAB错误、QNX post耗时、原车监测状态及窗口/pipeline变化。
4. 正常STOP并确认自有窗口/import消失；对比提示是否消失、原车内容是否继续刷新。若提示持续，保留原车故障记录，不清码掩盖。
5. 如果证明是自有窗口干扰，修自有布局/共存接入与资源分配；如果证明是原车图传/心跳异常，修对应会话冲突。根因明确前不提高z遮提示、不伪造健康心跳、不关原车监测。

固定图标仍能显示只能证明部分显示可见，不能作为全部行车信息正常的验收。先前地图可见和STOP资源释放通过也不能代验本次告警闭环。
