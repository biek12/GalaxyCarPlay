# 旧覆盖投屏法：归档边界与重构计划调整

## 用户新决定

2026-11-12用户原话：“新版本需要将原有的覆盖投屏法直接归档（代码归档保留，但不提供实际入口，也不提供注入投屏，所以这一块不用进行重构）”。

生效：旧整屏覆盖/遮罩投屏退出新版功能，源码归档保留，停止其专用结构重构。这是产品范围收缩，覆盖旧“保留完整遮罩”的要求；不是等待模型/技术探索通过，也不再为旧方案补新功能或美化。

## 本次追加与实施任务

用户进一步明确：“这条链条里的 AutoService 也需要停止相关注入，随后请开始发布新的重构任务”。Lead已完成旧启动/恢复/IPC/Root进程与共享依赖盘点，形成[R0确定任务书](R0-整屏投屏归档任务书-20261112.md)及[标准用例](R0-标准用例-20261112.md)，本批交DSH实施，实际派发以任务父目录DISPATCH回执为准。旧整屏停注入覆盖AutoService，但原厂Hook保留；QnxClusterHook仍复用receiver-candidate的hook-health功能，不能直接删除共享资产。当前尚未实施产品代码，不将派发当作完成。

## 已确认的保留范围

用户已明确答复：“**只归档整屏投屏，原厂元素增强保留**”。原厂音乐卡片、背景元素替换及其Hook、简洁配置页与卡片本地预览继续保留。这里只撤下旧整屏覆盖/注入输出，不停用原厂增强。

共享依赖需要特别区分：`AutoContract.MAP`仍承担CarPlay数据生产，不能为了关闭旧仪表输出直接删除此角色；`InstrumentMusicPreview`仍使用`theme.SceneData`；背景选择器也被原厂图片替换使用。CarPlay主屏/USB/无线会话、原厂元素背景数据、歌词和封面保留。关闭的是旧仪表整屏输出需求及其专用编辑制作入口。

正常撤销/资源释放仍是归档收口职责；不因“停止重构”跳过释放，也不将旧配置静默改成原厂元素方案来自动启动增强。

## 重构台账调整

- C2b撤销；C2后续凡只服务整屏主题库/编辑器/组件库/Canvas主题制作的任务不再派发。
- 旧THEME/PREVIEW/覆盖投屏链只做归档和入口关闭，不再做B1/S1原有整屏链的结构优化；当前基础服务、车辆订阅、媒体、公共UI及仍在范围内的原厂能力独立继续。
- 原标准用例是旧产品合同的历史证据。归档收口完成时须以“旧入口不能启动、旧配置/恢复不能复活、归档摘要一致、共用能力正常、实际编译/必要标准用例通过”验收；不要求为了通过旧断言重新开放旧入口。
