## 可确认的消耗来源

1. **对话和工具结果持续累积是最大部分。** A1/A4 对话历史约占当前上下文 89%/91%。A1 有81次 Read、46次 Shell，15条命令涉及 Gradle、11条涉及 formatter；A4有134次 Read，其中 AutoService48次均为有界片段，并非48次全文读取。这些包含必要工作，不能逐次认定为浪费，但大任务反复读写/调试会持续增大后续上下文。
2. **开工前固定上下文已约3.7万估计Token。** 除规则外还包括系统、工具、技能、MCP和子Agent定义。规则约1.3万，技能+MCP约1.6万。已检查样本的子Agent数量为0：有定义开销，没有证据表明这些任务因实际多Agent并发计费。
3. **项目规则混入历史流水账。** 根AGENTS约2.8万字符，自动refactor规则还重复任务经过，并要求读旧首轮任务/总控。Service/Cluster项目规则在仅改Client时也设为alwaysApply。长规则加上历史必读会增加初始上下文和重复解释，旧“当前任务”并列还会分散定位。
4. **修复入口缺少调试与最终验收的明确区分。** 最终整包门槛必要；定位两个已知测试错误时应先定向验证，成功后再跑完整入口。成功日志/完整JUnit/大diff若持续回显，会增加对话负担。先前日志有多次失败定位，但不能据文件数量推算额外收费金额。

Cursor 会把适用规则加入模型上下文；alwaysApply每次会话适用，globs可限制到相关文件。官方建议使用短而聚焦的规则、引用按需材料并避免重复复制规范。[Cursor 规则说明](https://cursor.com/docs/rules)
