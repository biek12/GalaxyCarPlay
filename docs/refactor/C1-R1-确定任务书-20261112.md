## 2. 唯一行为修复：一个调度pump与一个最新待执行请求

现有生产入口已经定位：Presenter构造一个单线程执行器并传入`BackgroundImageImport`；导入器`importImage`替换pending后却逐次提交drain。保留同一导入类/owner，不另建服务、队列管理器或导入框架。

按以下确定方案修`ui/BackgroundImageImport.kt`：

1. 在现有lock保护下增加一个“pump已排入/正在运行”的布尔标志。`pending`仍仅有一份最新请求。每次import只替换pending；**仅当标志原为false时置true并向executor提交一次pump**，已有pump时不再execute。
2. pump循环在同一lock内取走并清空最新pending，然后在锁外执行原runJob。运行期间新请求仅覆盖pending，pump完成当前任务后继续取最新的一份；找不到pending或closed时在锁内复原标志并退出。取pending与退出/标志交接必须同锁，避免丢失唤醒。
3. 保留generation校验：旧运行任务可收尾，但不能交付旧结果；新请求用原validateAndSave/原始bytes/AtomicFile流程，不能换成只缓存文件名或跳过读取。容量1待执行图片与最多1个已排入/运行pump是两个层面的合同，默认执行器和测试调度都必须满足。
4. close在同一owner释放pending并使代次失效，继续shutdownNow自有ExecutorService；正在收尾或已post的回调不触UI/写配置/发命令。若execute抛出拒绝异常，复原本轮调度标志并保留原异常，不留下永久“已排入”的假状态；不另建重试/回退路线。

无需改Presenter的页面/状态/持久化/命令行为，不调整旧图片参数，也不重建页面和预览。若只为删除不再使用的import，可随下方格式化处理。
