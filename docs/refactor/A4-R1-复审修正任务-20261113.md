## 3. 必修生产回归：上传租约失败必须留在资源异常边界内

### 缺陷与证据

`ipc/AutoServiceBinder.kt`当前410–413行：调用线程dup后，enqueue里先`clients.require(owner, calling)`，然后才`remote.upload(lease, ...)`。原`78feda1`的upload `try`包住了 **require Lease和桥接上传**，所有异常都会关闭copy并回「媒体上传不可用」。迁移后require抛错只进入ServiceRequestQueue错误处理，RemoteSession的catch不执行：失去原错误回执，同时copy没有关闭路径。

Codex忽略目录探针通过交付的真实AutoServiceBinderTest装配、IAutoService.Stub.asInterface、真实main队列，传未登记owner：预期error=「媒体上传不可用」，实际null，1例1失败。原输入FD仍有效。副本泄漏结论来自实际异常边界和源码路径，不冒充FD数量实测。

### 确定修法

1. `ServiceRemoteSession`借用与其他owner相同的`ClientRegistry`，构造显式传`clients`，不新建注册表。以同一Registry查询迟到Lease对象身份，代替测试可以无条件true的leaseAlive注入。
2. `RemoteSession.upload`入口改收`owner: IBinder, calling: Int`及原上传参数/copy/result；在 **同一个原try内**先`clients.require(owner, calling)`，再获取桥/调用upload，回调仍main→`!closed && 当前同一Lease`→callbacks。
3. Binder保留调用线程包名/正则/direction/长度验证和dup，enqueue中直接把owner/calling/copy交给RemoteSession；不要在owner的try外再做一次可能抛出的Lease校验。
4. 统一保留这条上传路径原catch：close副本、callbacks中runCatching回原中文错误。不得使用未授权Lease上传；不得只加catch吞错、只打诊断日志、直接关闭原输入file，或重复关成功移交的copy。
5. AutoService装配、ServiceRemoteSessionTest、AutoServiceBinderTest以及构造RemoteSession的Publication测试同步传同一个真实Registry。Web request与授权/disable/销毁的现有顺序保持，不能借本项改变这些非上传分支。

### 必须通过真实Binder的回归

可合并为参数化场景，但断言必须观察生产回调和资源，而不是检测源码字符串：

- 正确包名、合法输入、未登记owner：只回原上传错误，副本已关闭，原输入FD仍归调用者，不触发Web upload。
- 调用时owner有效，排队后先detach再执行main：同上；另测UID与登记Lease不符，同样不得漏资源或失去回执。
- 有效Lease、桥为空/桥upload抛错：副本关闭且原错误不变；不能只测直接调用RemoteSession的桥异常，而漏掉Binder到Lease的路径。
- 成功路径：WebPort实际收到可用副本，原FD有效；桥接管副本后关闭，结果按原队列回送。成功后先移除/替换Lease再触发迟到reply，不发布或回执旧Lease。
- 观察队列失败回调：上述原本应由upload接住的错误，不能仅变为ServiceRequestQueue失败。系统dup/close可用Robolectric系统边界记录，不能重写upload逻辑或给生产代码加FD计数状态。
