# Common 现有 UI 的复用与补充封装

用户本轮补充：“common 中确实有 ui 组件代码，其实可以复用这些，ui 模块中只需要补充封装。”本表已据实际源码核对，约束U1及以后所有UI批次。复用不只看名称；必须保留原行为并消除重复实现。

## 1. 已有实现，不重新建设

当前基线`ae02683`包含此前从`galaxy/common`迁出的代码。其父提交中`L7SettingRow`仍有原测量实现，`L7ModalDialog/L7DialogFocus`仍有原弹窗/焦点逻辑，可用Git追溯。当前`ui/GalaxySettingRow/GalaxyModalDialog/GalaxyDialogFocus`就是这条实现线；U1继续它，补静态XML/资源封装，不能推倒重做。

## 2. 根 common 的现成组件

已核对`common/src/main/java/com/shilapi/xcertplay/settings/SettingsWidgets.kt`和`SettingsTheme.kt`：有category header、开关行、选项行、分辨率slider等。其theme来自DiPlayPalette，slider直接依赖CarPlayDisplayScale和宿主R字符串；存在OVERLAY/CARD两种上游语义。它们是真实已有组件，后续页面需要相应能力时优先沿源码复用，不让Agent凭需求名称再造。

本轮Flyme自有页面已经使用上表L7组件线，U1不把它改成另一套上游CARD/OVERLAY样式；不重写根common、不删除上游组件、不强迫其跟随Flyme控件样式。以后若需要slider等跨应用能力，由Lead先拆出与CarPlayDisplayScale无关的纯参数/事件封装，保留业务换算在宿主，再给确定任务。U1没有使用slider，不提前创建它。

实际依赖是 `:common → :auto-ui`，因此不能为了复用写成`:auto-ui → :common`。跨App需要且尚未解耦的纯UI只能一次迁移/下沉，再让common保留兼容委托；无需跨App的原控件直接复用现有宿主入口，不迁移。禁止复制两份、通过反射访问internal类或用相似新控件绕过现有实现。

## 3. 交付核对

METHOD_MAP逐项列“原common类/方法→当前实现→本次仅新增封装/资源→调用方”。UI实现的测量、焦点、确认和回填规则尽量保持原代码；静态节点迁XML，样式取既有tokens。既有兼容调用方和XML新调用方必须一起编译，通过真实公共控件/Cluster用例。不能用一张“已复用”表掩盖仍然存在的重复工厂。
