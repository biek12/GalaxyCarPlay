本机没有QNX SDP，用户已确认没有环境。QNX正式SDK目标编译尚未完成。候选使用显式独立的最小接口声明、目标`_init_libc`接点和四个系统ELF的导入符号核验；不使用Android libc头、不复制OEM库，也不将该方式标为SDK正式编译。

QNX认证仍沿前次用户授权的原厂流程，通过指定外部样本在内存中使用；包内没有登录口令或该OEM样本。`tools/hab/telnet_session.py`支持显式IP、命令与压缩传输；指定`qnx_auth_apk`时只读取已核验来源的登录账号和密码，绝不执行其中录音/删除流程，认证不输出到日志。

## 本机重建

```sh
scripts/build_apk_fast.sh
python3 scripts/build_hab_probes.py --qnx-rootfs /absolute/path/to/captured/rootfs
python3 scripts/prepare_vehicle_test.py --qnx-rootfs /absolute/path/to/captured/rootfs
python3 /absolute/path/to/package/verify_bundle.py /absolute/path/to/package
```

以上不连接设备。打包脚本只assembleDebug及原生编译，不调用lint或整套单测。`build-report.json`核验ELF64/LE/AArch64/PIE、加载器和DT_NEEDED，并逐项确认QNX动态导入存在于指定系统库。链接元数据只留本机构建目录。

## 传输与启动

1. 本机先运行包内摘要校验。Android包解到`/data/local/tmp/`下，QNX包解到`/var/data/`下本次唯一目录；进入解出的包目录。目标QNX的`/tmp`指向`/dev/shmem`，其虚拟目录不能按普通文件系统mkdir/chmod；批量脚本与日志使用已核验的`/var/data`独立目录。使用已有授权Telnet通道传输，先校验目标文件摘要再chmod/执行。不要从带noexec的共享目录直接执行QNX程序。
2. 本车已核验的共享文件桥是Android `/data/vendor/nfs/nfs_ota` ↔ QNX `/otaupdate`；仅放本次唯一命名临时文件，QNX复制到本次`/tmp`目录后再执行，不替换已有系统文件。
3. 分别开一个Android和QNX shell。先两端self-test，再QNX inventory，随后按下列先后次序运行。脚本使用本车QNX display ID2、1920×532、z-order4；这是本次目标测试输入，不自动适配其他车型。

| 阶段 | QNX shell | Android shell | 期望 |
| --- | --- | --- | --- |
| 启动/算法 | `sh qnx/run.sh self-test` | `sh android/run.sh self-test` | 各自`SELFTEST_PASS`，不打开HAB/创建窗口 |
| 只读显示枚举 | `sh qnx/run.sh inventory` | 无 | 应包含display ID2、1920×532；不创建可视窗口 |
| 双向消息 | **先**`sh qnx/run.sh transport` | **后**`sh android/run.sh transport` | 双向64B fixture校验，收发与close均0 |
| 帧与Screen | **先**`sh qnx/run.sh receive` | **后**`sh android/run.sh frames` | receiver准备可写buffer后ACK；六帧红/绿/蓝/白色条，底部黑标移动；正常STOP后恢复原车画面 |

`run.sh`记录本次child PID和独立日志。人工色块模式发送端固定6帧、间隔1000ms，`receive`接收端最多处理120个事件。App模式用`sh qnx/run.sh serve <显式配置的app-owner.key>`，等待连接10分钟，会话无帧5秒或收到STOP后释放自身窗口退出；下一会话显式重启。公开fixture不能代替应用自有key。

## 日志与退出

- `logs/android-frames.log`检查`SENDER_AUTH_INIT_ACK=0`、每帧result0、`SENDER_STOP_CLOSE=0`。
- `logs/qnx-receive.log`用`BEGIN`/静态操作名/`RETURN`定位最后一次平台调用；检查`RECEIVER_READY_ACK=0`、`screen_post_window`返回0、close及unmap/unimport/VC释放结果。日志不输出指针、认证字节、协议载荷或手机/车辆标识。
- 若等待不结束，先在Android运行`sh android/stop.sh`，再在QNX运行`sh qnx/stop.sh`。脚本先核对PID所属程序，只向本次进程发送TERM，不killall、不终止原车Screen/HMI，也不自动SIGKILL。仍存活时保留PID/日志供继续定位。
- 测试前后各运行对应`snapshot.sh`，比较原车窗口的display/尺寸/order/status；该脚本只取限定字段，不抓全量getprop、logcat或slog。
- 人工色条正在显示期间如需截图，在QNX独立shell显式运行`screenshot -display=2 -file=/tmp/<本次目录>/logs/test-pattern.bmp`。截图应与post/窗口属性共同核对；仅`send=0`或`post=0`不能单独证明物理仪表可视。

判定顺序：ELF启动 → 算法自检 → HAB消息 → AUTH/INIT/ACK → 共享帧 → Screen post → 截图/人眼确认 → STOP释放 → 原车恢复。完整CarPlay111地图及独立音乐/歌词合成已接入新版APK，编译/安装与内容实测分开记录；旧人工色条通过不等于本次完整内容验收。
