# HAB先直连、后准备：接收端复用优化

2026-10-30。用户提出：接收程序已部署后，应先尝试HAB连接，通了就不等待ADB/Root和QNX登录。这一方向可由现有源码支持，本轮已据此调整Android启动顺序，未连接或操作车机。此前[整改实施](AutoService整改实施-20261030.md)为前一构建记录；本轮不改变QNX C实现、窗口布局、HAB协议或原车启动项。

## 现有材料实际支持什么

| 证据 | 结论 |
| --- | --- |
| [`qnx_probe.c:89–116`](../tools/hab/qnx_probe.c:89)的`serve`模式 | 正常STOP后先关闭本代窗口、PMEM、VC，再在同一进程等下一次连接；不需要每次都登录QNX重启 |
| [`qnx_probe.c:95、112–115`](../tools/hab/qnx_probe.c:95) | 监听open预算每次600000ms，连续三次建链/空会话失败退出；认证/协议错误立即退出。安装文件仍在，不代表进程一直监听；也没有QNX重启后的自动启动配置 |
| [`galaxy_hab_sender_open:55–84`](../galaxy/service/src/main/cpp/hab/galaxy_hab_sender.c:55) | HAB open后仍需共享内存export、AUTH、INIT和ACK。只判断设备文件存在、进程启动或pipe可写不够；成功的会话可以直接继续送帧 |
| [`galaxy_hab_qnx_open:204–235`](../galaxy/service/src/main/cpp/hab/galaxy_hab_qnx.c:204) | 接收端验证认证及display/尺寸/z-order，完成PMEM导入与窗口buffer准备才发ACK。快速复用不绕过这些核验 |
| [`galaxy_hab_linux.c:15`](../galaxy/service/src/main/cpp/hab/galaxy_hab_linux.c:15) | Android发送端需要`open("/dev/hab", O_RDWR)`和后续ioctl。驱动实现没有在本项目里写死UID0；普通App是否允许以实际建链结果判断，不预先强制走Root |
| [既有稳定性记录:17](HAB连接稳定性修复-20261030.md:17) | 历史记有独立应用UID的一帧/STOP成功；支持保留普通应用接入。但不能代验新AutoService包名、当前权限/SELinux域和本轮APK |

因此可以省掉**成功连接前的QNX控制面与Root等待**，不能概括为“QNX安装一次，此后永远无需恢复”。接收端退出、QNX重启、首次安装、owner key改变或配置不兼容时仍需自动准备。

## 本轮改动

```text
AutoService启动后恢复已选仪表 / 客户端提出投屏需求
  → 普通App直接启动自有HAB sender，完成原AUTH/INIT/ACK
     → 成功：保留同一进程/VC直接送帧，不等待Root/权限配置或登录QNX
     → 失败：先回收该发送进程，再尝试现存自有UID0 helper
        → 成功：直接复用接收端，不登录QNX
        → 失败：等待基础Root准备，自动定位认证来源并校验/准备QNX receiver
           → 再建立真实HAB会话，握手通过后送帧
```

这两种Android执行身份使用同一套HAB协议和输出实现。不是新增备用输出路线，也不通过chmod放开设备权限。普通直连成功后，车辆采集所需的Root维护仍在独立后台进行，失败/未就绪不会打断已建立的普通App HAB会话。

- [`AutoService.updateProjection:252`](../galaxy/service/src/main/java/com/ecarx/autoservice/AutoService.kt:252)有实际投屏需求便激活连接，取消原先`platformReady`串行门控。没有消费者时不为“碰撞”分配共享区、图形缓冲和持续心跳；开机恢复独立仪表时首个投屏需求自动触发。
- [`GalaxyHabComposition.connect:138`](../galaxy/service/src/main/java/com/ecarx/autoservice/projection/GalaxyHabComposition.kt:138)按普通App→现存helper→必要准备顺序执行；[`GalaxyHabSessionStart`](../galaxy/service/src/main/java/com/ecarx/autoservice/projection/GalaxyHabSessionStart.kt:8)保证成功就返回原会话，取消或旧owner未释放时不启动下一个owner。
- [`GalaxyHabProcess.awaitReady:50`](../galaxy/service/src/main/java/com/ecarx/autoservice/projection/GalaxyHabProcess.kt:50)只认自有native在AUTH/INIT/ACK后输出的完整READY，沿原native的10秒open/12秒alarm保留12秒有界等待；不是新开一个裸连接探测后立即断开。EOF/关闭状态会使后续送帧失败并进入现有有限恢复。
- [`RootHabProcess`](../galaxy/service/src/main/java/com/ecarx/autoservice/platform/RootHabProcess.kt:13)改为通过stdin半关闭请求退出，并等输出EOF；[`RootHabSession`](../galaxy/service/src/main/java/com/ecarx/autoservice/platform/RootHabSession.kt:12)在关闭连接前回收自有子进程。避免上一尝试尚在驱动open时下一尝试并发抢到通道。
- [`PlatformCoordinator.prepare(false):65`](../galaxy/service/src/main/java/com/ecarx/autoservice/platform/PlatformCoordinator.kt:65)不再登录QNX杀掉接收程序。正常退出由native STOP释放窗口并回到既有有限监听，异常断线仍由QNX的5秒会话接收期限释放；不持续占屏。确有建链失败才运行原有部署/恢复流程，并使旧listening缓存失效。

QNX程序的有限监听策略保持原样，没有添加永久守护或改原车init/HMI。当前直连成功也不代表确认接收程序二进制SHA与包内相同，只证明同一owner key与既定目标profile下的现有协议握手成功；本轮不强制替换仍兼容工作的receiver；需要特定版本时仍须进入准备/部署流程，不能用握手结果声称二进制摘要一致。
